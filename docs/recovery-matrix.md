# Recovery matrix

Kawai's recovery behaviour, one row per fault (execution-safety-recovery D17,
contract E7). Each row names the mechanism that recovers from the fault, the
OpenSpec change that owns it, the contract it rests on, and the test that
proves it — or `gap — <reason>` where no mechanism or test exists on master.

Sources: every row of the durability table in
[`multi-agent-development-ux.md`](multi-agent-development-ux.md) ("Durable
recovery and idempotency"), its R17–R19 scenarios, this change's own capture,
backup, and migration faults, `revision-control`'s R1–R4 contracts, and the
D11 late-writer and exclusive-slot invariants.

**The rule (AGENTS.md):** a change that adds a recovery mechanism or an
exclusive slot adds its row here in the same change, naming its test. Every
exclusive-slot holder kind ships a liveness predicate and startup clearance of
orphan holders, run again whenever the slot is found taken; no leases, epochs,
or fencing tokens (D11).

**Test citations** are `` `file` › `title` ``: the file path from the
repository root and the exact title of a `test`, `it`, or `describe` in it.
`src/server/__tests__/recoveryMatrix.test.ts` parses this table under
`bun run test` and fails when a named file is missing, a file lacks the title,
or a row has neither a citation nor a gap with its reason.

## Measurements

Taken on the dev host on 2026-10-18 for tasks 3.4 and 6.3; they describe the
cost of the mechanisms above, not a guarantee.

- **Audit hook cost per audited call (task 3.4).** With the fixture adapter
  calling the hooks the live `ChatSessionDriver` registered (in process, no
  control protocol), over 5,000 Bash calls cycling through six commands (a
  push, a `cd` chain push, a `curl` send, `npm publish`, `gh pr comment`, and
  a non-send `ls`): PreToolUse p50 6.2 µs, mean 8.6 µs, p99 45 µs;
  PostToolUse p50 0.7 µs, p99 3.7 µs. Task 3.4's synchronous-parse
  measurement was ~10.3 µs per call. The real CLI adds one control-protocol
  round trip per hook event over its stdio pipe; the fixture adapter cannot
  measure that, and it was not measured against a live CLI.
- **Backup pause (task 6.3).** On a 5.7 MB database, `serialize()` held the
  connection for 1.8 ms at the median (1.6–4.3 ms over 20 runs). A whole
  snapshot — copy, `.partial` write, fsync, rename, and the integrity check on
  its own connection — took about 10 ms (9.3–19.8 ms over 5 runs); only the
  `serialize()` part blocks the server's own writes.

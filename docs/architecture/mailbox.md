# Team mailbox

Teams, the kawai-team MCP server, threads, mailbox management, waiting reasons, delivery receipts, and message events. Part of [the architecture reference](README.md).

- Mailbox recovery also runs when a recipient finishes a turn, fails, is archived, or is killed: recorded receipts settle; unconfirmed pushed mail is held for review. In-flight claims remain visible as Receiving. Retry refuses a killed recipient, and killed-sender thread context includes only confirmed delivered messages. `/clear`, `/reset`, and `/new` clone an existing chat’s stored group even when its definition is missing; ordinary creation still refuses unknown groups.
- Agent teams share one git repository, including linked worktrees; plain directories form their own team. Role groups load from the main checkout's `.kawai/groups/<id>.md`, layered over `~/.kawai/groups/`. A chat chooses its fixed group at creation. Its role body and mailbox note are re-read only when its agent starts; a missing group keeps its badge but receives no new group mail.
- Each chat has an in-process `kawai-team` MCP server with `send_message`, `reply`, `schedule_message`, and `list_groups`, allowed without approval cards under either policy. Kawai supplies sender identity, group, and origin path; recipients must belong to the same team, and direct mail restores an archived recipient. Messages persist in SQLite and arrive as peer turns with a message id and thread. Normal mail waits for an idle agent with no pending card or live worker; urgent mail comes first, direct before group, then oldest. Group mail goes to the longest-idle member exactly once. Urgent direct mail interrupts only after pending cards resolve and the SDK confirms interruption; urgent group mail waits for idle. Scheduled mail survives restarts.
- Replies keep their thread: an archived sender is restored; a killed sender's reply falls back to its stored group with the full thread, or is dead-lettered if no group remains. Queued direct mail to killed recipients is dead-lettered. Threads stop at the sender group's `hopLimit` (default 20); a human retry resets the hop count.
- Mailbox management (`team-mailbox-management`): the `kawai-team` server also carries `list_mailbox`, `cancel_message`, and `discard_message`, allowed without cards and refused by right at each call from the caller's current group file (`src/server/team/mailboxManagement.ts`). Any agent lists the unsettled mail it sent, received, or holds and cancels its own mail while queued, scheduled, or awaiting a request; a `canManageMailbox` group sees and cancels any team message in those states plus `parked` work, and discards `dead`/`uncertain` mail. Claimed, spawning, and delivered mail is never cancellable; retry and hand-off stay human-only. Agent cancel and discard require a reason (cut to 300 characters; the row's `reason` reads `cancelled by <session>: …`), refusals name the state or missing right and write nothing, and another team's ids read as not found. `MailboxStore.cancel(id, actor, reason?)` is the one path for the human panel and agents: the store keeps one invariant, parked work always has a live resume or is cancelled with it: a parked cancel cancels its `queued`/`awaiting-request` resume in the same transaction (so a resume can never deliver after it), is refused with `resume-in-flight` (holder named) while the resume is claimed or delivered, and a resume linked to parked work refuses every cancel (`linked-resume`, parked id named) — kawai's own re-park, unpark, release, and forward go through `replaceResume`; a cancelled holder is un-paused but neither restored nor resumed, and `LimitOutcomes` defensively drops work that is no longer parked or delivered. The event log's actor vocabulary is `system`/`human`/`agent`, the last with a nullable `actor_session` column (additive; old rows null), kept separate from the task journal's author and from `TeamActor`; a task-bound cancel appends a journal note authored by the acting agent. The Mailbox tab offers Cancel on parked rows beside Hand off and shows each row's short id (first 8 characters, full id copyable).
- Task mail: `send_message`, `reply`, and `schedule_message` take an optional `task_id` of the sender's team (unknown or other-team ids are refused and nothing is queued); a reply without one keeps its original message's task. The task context is built when the message is delivered, not when it is sent, so it reflects amendments and notes made while it waited: the envelope metadata gains `task` (`id`, `title`, `status`, `revision`, `direction`, `acceptance`, `openspecChange`, `worktree`, and `journal` — the last 5 entries, each cut at 500 characters; `task_get` has the rest), and a readable header precedes the body, stating that a linked OpenSpec change's proposal, design, and tasks are the authoritative direction. Envelopes without a task keep the old shape. Receiving task mail associates the session with that task (`chat_sessions.task_id`), which its chat header shows; a spawned member keeps the task it was spawned for.
- Waiting reasons (team-waiting-reasons): the Mailbox tab shows every unsettled state with exactly one section, in a fixed order — Held for review, Dead letters, Parked, Starting agent, Queued, Receiving, Scheduled — the first three expanded by default and the rest collapsed behind their counts; a search narrows every section over participants, bodies, and reason text, empty sections can be hidden, and routing state is its own collapsible section. Each unsettled row carries a server-computed reason: an immediate blocker plus the other constraints that also apply, ordered deterministically with capacity first (group cap, per-profile cap, team spawn cap, worktree occupancy), then member facts, then spawn/routing specifics; a `spawning` row's blocker is always Starting agent, its own reservation's capacity effects listed among the others. Reasons are derived from the same dispatch, staffing, and routing state that makes the delivery decision (a cause reporter beneath the unchanged eligibility/claim predicates; the router's `none`/`hold` carry a diagnosis; direct mail reads the recipient view), held in memory only (rebuilt by the first pass after a restart, never persisted), refreshed on every dispatch pass, and re-published when a team's reasons structurally change — including reason-only changes with no row state change. `team-mailbox-snapshot` carries them beside the worktree occupancy roster (`worktrees`: live sessions per resolved worktree root plus pending reservations — manual sessions listed, only spawned ones and reservations counting as writers). Dead letters show readable labels for known codes (`worktree-missing`, `killed-recipient`, `killed-sender-without-group`, `hop-limit`) with the raw code still visible; unknown codes render verbatim. Named sessions in reasons link to their chats; worktrees show their basename with the full path available.
- Mail delivery is acknowledged only by the recipient's complete CLI transcript row carrying its id, never by a push or display event. Startup reconciliation requeues unpushed claims, confirms recorded receipts, and requeues a pushed message absent from a clean transcript. Missing, unreadable, or torn transcripts hold the message as uncertain for human resolution; retry targets the same recipient with a possible-duplicate notice, or the human explicitly discards it.
- Every message state change is recorded in the append-only `team_message_events` table (`messageEvents.ts`, written inside `MailboxStore`'s transitions so none can escape logging): `sent` (or `dead-lettered` when the hop limit is already over), `reserved`, `claimed`, `held-for-request`, `pushed`, `delivered`, `requeued`, `held-uncertain`, `retried`, `cancelled`, `discarded`, `dead-lettered`, `parked`, `unparked`, `released`, `forwarded`. Each row carries a per-message sequence, the actor (`human` for the composer's send and the UI's cancel/retry/discard, `system` for delivery, recovery, and limit outcomes), the facts the update overwrote (previous state, claimant, recipient, reason), and the reason the transition wrote. Events are durable rows that survive restart with their messages; history reads one message's events or every event of a thread.

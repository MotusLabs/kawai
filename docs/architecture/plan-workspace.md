# Plan workspace

Workspace records, the read-only workspace view, and the repository conversation. Part of [the architecture reference](README.md).

- Plan workspace records (plan-workspace PR A, `src/server/plans/workspace/`): migration 19 `plan-workspace` adds the four tables; `PlanWorkspaceStore` holds the durable Architect/Lead bindings (CAS writes, the version only grows, no unbind), `PlanWorkspaceRefs` the labelled document references, and `PlanWorkspaceContext` the immutable per-message context snapshots keyed `(session_id, message_uuid)`. Bind, ref-add, and ref-remove are keyed commands on the shared `(team_id, command_id)` ledger (`commandLedger.ts`): the same kind and payload replays, a drift is refused naming the field, and a refusal writes no row, so a resend is evaluated afresh. The `team-plan-workspace-*` messages (`workspaceConnections.ts`) resolve `teamPath` through `TeamScopes`, re-push the snapshot after every committed write only, and start no agent.
- Plan workspace view (plan-workspace 5.x, `src/client/components/team/PlanWorkspace*`, `teamPlanWorkspaceStore`, `planWorkspaceMarkdown.ts`): the Plans detail's **Workspace** section is read-only and starts no agent — it projects, never dispatches. The **map** lays the displayed version's changes out as a deterministic WBS table (rows in plan order, columns by dependency depth) with each change's edges, holders, checklist totals, and execution state as separate facts; invalid dependency data (a cycle, an unknown dependency) renders a flat diagnostic list naming the unresolved changes and one cycle's path, and a text alternative lists prerequisites and dependents per change for keyboard and screen-reader users. **Checklists** expand per change as a read-only projection of the change's canonical tasks artifact (checked states and source lines, no editing) and show the named unavailable states instead of fabricated items. **Canonical artifacts** (`PlanWorkspaceArtifacts`, §5.3) lists the selected change's proposal/design/tasks/spec descriptors as the resolver enumerated them — active main or convention-worktree source named, archive entries labelled, every unopened row reading `unread` and every hash/size/availability fact coming only from the selected document-open — while the enumeration's subscription follows the selected change (a selection, plan, team switch or unmount sends `artifacts-close`) and a refused enumeration (missing, missing-in-worktree, ambiguous, cli-unavailable, uncontained) renders its fixed path-free reason. **Documents** open one at a time from labelled references with full provenance (worktree, path, content hash, size) and the explicit current / last-valid / missing / unsupported states, plus the selected execution's artifact-pin match; relative links and images navigate inside the reader through scoped resolvers (external https opens separately, every other scheme, an escape past the worktree, and anchor-only targets render inert with a reason), and the scoped asset route serves image bytes — the displayed version (approved, else newest in review, else newest draft, or picked) and the execution are chosen explicitly in the section's pickers and never implied. **Agent health** shows passive context and quota dots (green below ~70% context with an applicable fresh quota, yellow ~70–90%, red above; stale, reset-passed, disconnected, and excluded account-source readings read unknown and stay inspectable in the disclosure) — never a prediction or a dispatch input. Opening the workspace never starts, restores, attaches, or refreshes a worker.
- Repository conversation (plan-workspace §6.2–6.4, `PlanWorkspaceConversation.tsx`, `planWorkspaceScopeStore.ts`, `planWorkspaceResetTransfer.ts`): the Plans view embeds the shared ChatSurface under two durable **repository roles** — Architect (planning conversation) and Lead (coordination conversation) — the team's bindings from design D6's `plan_workspace_chats`. A role is a label, never an authority: binding is an explicit human act (pick an existing same-team ordinary chat — never the other role's session — or create one through the normal New Session dialog, bound only after the created `session-created` is observed; the panel shows the bound chat's group/profile/approval and warns when the plan's execution `leadGroup` differs from the bound Lead chat's group, while execution routing and decisions keep following the plan); an archived bound chat renders read-only with the ordinary Restore, a killed/unavailable one stays visible until an explicit replace, and the panel never auto-creates, replaces, or guesses. Only the selected role's surface mounts, so exactly one conversation attaches (the inactive role's agent is detached without interrupting its work and is never started by the panel; observation is the snapshot). The **captured plan scope** (§6.3) freezes when a draft first becomes nonempty under the panel — later navigation never mutates it — rides the additive `chat-send.workspaceContext` envelope through the server's validators (V1–V8), shows above the message in the transcript, explains a selection mismatch with an explicit replace, and a refused send restores the draft text and the attachment without resending; the full-screen view sends unscoped. Two Lead-authorized contracts keep the panel live and refusals precise: the team bindings subscription (`team-plan-workspace-bindings-open`/`-close`, addressed by teamPath) pushes the roles lazily on panel mount, reconnect, and after every committed bind/replacement/reset transfer into one per-team bindings slot reconciled by CAS version (Q1); and a contextual `chat-send` may carry a client-minted bounded `requestId` that every refusal echoes with the session id, so the restore is correlated-only — no heuristic, no automatic resend — while sends without the field keep today's exact error shape; an accepted send answers with one acceptance on the sending connection alone, once the manager accepts, never a ChatEvent (Q2). A local `/clear`/`/reset`/`/new` transfers the old session's repository bindings to the created replacement by the same CAS bind a human replace uses — exactly once, from either host, with the last observed version as the expected token; a concurrent replacement refuses it (`stale`), and with no observed snapshot nothing is sent (explicit rebind only).

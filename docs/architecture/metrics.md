# Process metrics

Agent-start provenance, per-turn usage, process observability, process metrics, reports and proposals. Part of [the architecture reference](README.md).

- Agent-start provenance (team-process-metrics D2, `src/server/metrics/`): each constructed agent query — first start, resume, and the driver's respawn after a crash — reports through the driver's `onSpawn` option (observational; a throw is logged, never fails the spawn) to the manager's `ProvenanceRecorder`, which writes one `agent_starts` row (session, team, group, profile, model, effort, cwd, time) with SHA-256 hashes from `provenanceHash.ts`: the group file in effect (`GroupCatalogEntry.file`, frontmatter included; null without a group), the system-prompt addition received, the worktree root's `CLAUDE.md`, and the Claude auto-memory directory — `<claudeConfigDir(launch env)>/projects/<team main checkout with every non-alphanumeric character replaced by '-'>/memory` (observed: `/home/coder/kawai` → `-home-coder-kawai`; linked worktrees load the main checkout's), hashed over sorted `relpath \0 sha256 \n` with each file's hash kept once per distinct directory state in `memory_manifests` (`INSERT OR IGNORE`); a missing input hashes to null, one that exists but cannot be read is listed in `unavailable`. Starts are never pruned; `latestStart(session)` names the start turns ran under.
- Per-turn usage (team-process-metrics D1, `src/server/chat/chatTurnUsageStore.ts`): `turn_completed` carries an optional `usage` (input, output, cache-read, cache-creation tokens from the SDK result; missing fields 0; absent in older history), and every completed turn of every chat — task-bound or not, with or without a group — writes one `chat_turn_usage` row (`INSERT OR IGNORE` on session + turn) with team, group, profile, model, `num_turns`, outcome, the task pinned at turn start, and the agent start that ran it. `TurnUsageTracker` pins on `turn_started` (the session's task then, its latest start) and repins to the delivered mail's task — or none — on that turn's `peer_message`; mail or association changes mid-turn never move a running turn or carry over; an interrupted turn writes nothing; an unpinned completion (begun before a restart) falls back to the session's task and latest start. Tokens only, never currency; usage spent by Task subagents and by turns that never completed is not counted. A failed write is logged and never affects the turn or mail settlement. Rows survive kill/archive and age out after 90 days (pruned at startup and at most hourly).
- Process observability foundation (`src/server/metrics/observations/`, `src/server/metrics/export/`): managed chat/task facts reconcile into SQLite after commit, with stable source keys and atomic lifetime totals. Live turns checkpoint every 30 seconds; phase time lands as per-phase totals on `turn_ended`, each tool call and approval or question is one row written at completion or turn close, and a resolution with no open request is only counted (`unmatchedResolutions`); restart closes the turn at the last known checkpoint as partial and records the unknown gap. Context samples coalesce except exact boundaries; missing usage/compaction measurements stay unknown. Fact observations and completed usage retain 90 days and intra-turn interval detail (tool, request, context, turn start/attribution) 14 days (`OBSERVATION_INTERVAL_RETENTION_MS`), in bounded batches, with `detail-retained-since` stating the 14-day cutoff and `facts-retained-since` the 90-day one; only durable-source keys (`isDurableObservationKey`: `usage:`, `source:`, `acceptance:`, `first-acceptance:`) enter the ledger and persist with the totals, every other key is deduplicated by the row's unique `source_key`, the team is read from `team_id` (compact-observation-detail D4/D5), pruned pages return to the file through incremental auto_vacuum, and a source row failing validation is skipped, never stalling its source. Post-commit notifications coalesce into one reconcile pass 250 ms after the first (an unref'd timer, cleared on stop). Optional same-listener `/metrics` needs `KAWAI_METRICS_ENABLED=true` and a nonempty bearer `KAWAI_METRICS_TOKEN`; invalid/disabled export never blocks Kawai. Provider-account quota, canonical stage and incident adapters remain pending and expose source capability 0. Definitions, bounded labels and operation: `docs/operations/process-observability.md`.
- Process metrics (team-process-metrics D4/D5, `src/server/metrics/`, model in `src/shared/processMetrics.ts`): computed per team at read time, never stored, over a window (`1d`/`3d`/`7d`) ending at the read, with the preceding window of equal length as its baseline. `metricsQuery.ts` loads once, in one read transaction: cohorts by in-range events over `[end − 2w, end)` (tasks whose first-ever `done` falls in range — a reopened task first done earlier never re-enters — status events, results, findings, mail sent or delivered, message events, turn usage), then their whole history by id (every transition, result, finding, recorded turn, task mail, and the agent starts of every session that did attributed work), plus limit events from 24 h before the range and park episodes opened before it. Pure families: flow (lead time to the first `done`, approximate for backfilled rows; mail wait from the later of creation and `deliver_at`, normal and urgent apart; nearest-rank p50/p90), quality (first-pass review yield — any failing finding on the first result fails it; finding fail rate; fix iterations; reopen rate), coverage (done tasks with a result, findings, an accepted result), overhead (mail share and task mail per done task by sender group, the human as `human`; friction: parked, forwarded, held-uncertain, dead-lettered events, with their messages), capacity (limit tax: cooling hours from `coolingTimeline` — the router's own rule — counted only for the profiles this team's own sessions hit, each profile's cooling read from its recorded events plus its provider's provider-scoped ones (providers-and-workers D8), clipped to the window, plus parked hours charged to the holder's profile; tokens by group and profile, and per done task from all its turns, marked partial when the task predates the usage horizon: retention, or the team's first recorded turn). Every value carries `n`, its baseline, and an insufficient flag below `MIN_SAMPLE = 10`; `n = 0` reads as no data. Fixed guard pairs: lead time ↔ accepted-result share; mail share, task mail per task, friction per task, fix iterations, finding fail rate ↔ reopen rate; tokens per task ↔ first-pass yield. Attribution sides (`slices.ts`): author (one owner per task — the submitter's latest start at or before its first result — owning first pass, iterations, and all tokens; `no result`; `mixed` counts later results from another slice value), reviewer (each finding's author), turn (the pinned start), sender (group only), team (not sliceable; limit tax by profile); slices are group, profile, group file hash, or one memory file's hash, `unrecorded` without a start. `MetricsReader` caches a read 30 s per (team, window, slice). Agents read it through `team_metrics { window, slice? }` (read-only, bound to the caller's team, allowed without cards; an unknown window is refused naming `1d, 3d, 7d`); the human through `process-metrics-open`/`refresh`/`close` → `process-metrics-snapshot` over the chat WebSocket, addressed by `teamPath` (`unknown-team` refused), re-sent on open, refresh (a fresh computation), and report or decision commits (`ChatConnections.publishMetrics`) — never on mail changes. The Team page's **Metrics** tab (`src/client/components/team/metrics/`, `metricsStore` keeping only the requested window and slice's snapshot) lives at `#/team/<key>/metrics/<window>[/<report id>]` — a location naming no window adopts the team's last (7d first) by replacing the entry, an unknown one with a notice — and shows each family collapsible with every metric's value, `n`, baseline delta, insufficient flag, guard, approximate/partial/not-sliceable markers, breakdown and slice rows, the caveats, `computedAt`, and Refresh; drill-down opens a task in the Tasks tab and a message's thread in the Messages tab; window, slice, collapsed families, and open drill-downs are per-team `teamWorkspaceStore` state; controls disable while disconnected.
- Process reports and proposals (team-process-metrics D6, `src/server/metrics/report*.ts`, `versionChanges.ts`, model in `src/shared/processReports.ts`; tables `process_reports`, `process_proposals`, `process_proposal_decisions`, `process_proposal_link_events`, `process_commands` from schema migration 7 `process-reports`; 8 `plan-execution`, the seven execution tables and `team_messages.allowed_profiles`): the `kawai-team` server carries exactly `process_report_submit`, `process_reports_list` (newest first, default 10, with per-window freshness), `process_report_get`, and `process_proposal_link`, allowed without cards and bound to the caller's team. Submit needs `canReportProcess` in the caller's current group file and takes a window, a summary, and proposals — each a `change` or `revert` of one target (a group's file, or one shared memory file by name), an edit, a rationale, and expected effects (a metric and `up`/`down`); window roles bound them (1d carries none, 3d only reverts, 7d both), unknown groups, metrics, and directions are refused, and a revert names a hash recorded earlier for that target at its own granularity (the group file hash, or that one file's manifest hash). Kawai computes and freezes the snapshot and period at submission; the author, team, window period, and snapshot are never arguments, and any refusal writes nothing. Only the human decides, once per proposal, from the Metrics tab (`process-proposal-decide`), recording the target's latest hash at or before the decision. Versions are derived per target from its ordered starts (a recurring hash is a new change, the first start none, starts that could not read the input skipped). Implementation is an explicit link to one version change after the decision whose hash qualifies (≠ the decision hash for a change, = `revert_to_hash` for a revert): the human links, replaces, and unlinks (`process-proposal-link`, `changeStartId: null` unlinks); a `canReportProcess` agent only links an accepted proposal that has no link to one of its candidates. Every link event is kept with its actor; proposals whose links name one change are marked shared. Human commands use the command protocol: one `process_commands` row per `(team, command id)`, the same payload replays the stored outcome without a write, a different one is refused naming the field (`process-proposal-result` carries `replayed` or `error`). No agent tool decides, applies, withdraws, relinks, or unlinks a proposal (`REPORT_FORBIDDEN_TOOL_NAMES`), and Kawai never edits a file to apply one. Outcomes and unproposed changes are derived at read time: an implemented proposal compares each expected metric on its own attribution side — work by starts that loaded the decision hash before the linked change against work by starts that loaded the linked hash from it on, over equal windows of at most 7 days — falling back to the team's windows, labeled not attributed, for team-side metrics or when no target start did such work; below `MIN_SAMPLE` either side reads undetermined. Unproposed changes are the window's version changes no accepted proposal's current link names. `process-metrics-snapshot` carries the newest 20 reports plus every older report still holding an undecided proposal or an accepted one without a link, the per-window freshness, and the window's unproposed changes, re-sent on every report, decision, or link commit (`onProcessReportChange`); any other report opens by id (`process-report-open`/`close`, answered by `process-report-detail`, `report: null` when the team has none) and is re-sent on every commit until closed, so a report URL keeps every proposal decidable, replaceable, and unlinkable. The Metrics tab shows Reports (freshness, newest first), Needs a link, and Unproposed changes above the families; `#/team/<key>/metrics/<window>/<report id>` shows one report — summary, frozen snapshot, and `ProposalCard`s with Accept/Reject and a reason, the link picker over candidates, Replace link and Unlink, the linker, the shared marker, link history, and the outcome — each command armed with one key in `metricsStore`, reused while its payload is unchanged and retired on success.

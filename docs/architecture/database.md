# Database safety

Migrations, startup refusal, and backups. Part of [the architecture reference](README.md).

- Database safety (execution-safety-recovery D13–D15, `src/server/dbSafety/`): `schema_migrations` records each applied version (number, name, time, build, pre-migration backup path) and `PRAGMA user_version` mirrors the highest, never read for a decision. `initDatabase` reads the version without writing; a database newer than the build is refused before any write (`DatabaseStartupError`: both versions, the newest `pre-migration-<n>` backup, `docs/operations/database-backups.md`; the server exits, no override). Then it takes the `startup` snapshot; only on a database with no recorded version it runs the frozen baseline (`baseline.ts`: `applySessionSchema` plus every store's schema function — stores never create their own tables, so store-level tests use `schemaDb()`) and records version 1 `baseline` (one transaction on a database with no tables, each step committing alone on a pre-version database); then each pending entry of `MIGRATIONS` (versions dense from 2: 2 `strategy-impact`, the strategy impact proposal, decision, and request tables; 3 `plan-validation`; 4 `task-status-events`; 5 `agent-starts`; 6 `chat-turn-usage`; 7 `process-reports`; 8 `plan-execution`, the seven execution tables and `team_messages.allowed_profiles`; 9 `outbound-audit`; 10 `context-exhausted`, the two `chat_sessions` flag columns and `team_exhaustion_episodes`; 11 `process-observations`, the observation/checkpoint/alias/aggregate tables; 12 `provider-limit-window`, the nullable `provider_id` and `limit_window` columns on `profile_limit_events`; 13 `integration-candidates`, the integration branch, candidate, promotion, and promotion-effect tables with the one-running-promotion index; 14 `process-observation-indexes`, the `ended_at` index on `chat_turn_usage` and the `at` index on `profile_limit_events` behind the observation reconciler's ordered scans; 15 `codex-chat-runtime`, the creation-fixed `runtime` and `codex_home` columns on `chat_sessions` plus the `transcript_path` the Codex driver fills in, written at call time and never in an eagerly prepared statement so subset-migration opens still prepare; 16 `plan-supervision`, the decision card, decision, fix-task, and stall-alert tables; 21 `compact-observation-detail`, which deletes per-segment `activity` rows, tool and request start rows and unmatched request resolutions, drops `process_observation_teams` and every non-durable observation ledger key, and swaps the `team_time` and `task` observation indexes for `(team_id, seq)`) runs only after its `pre-migration-<n>` backup is renamed into place and passes its check, its `up(db)` and version row in one `BEGIN IMMEDIATE` transaction — a failed backup or migration rolls back and refuses start naming both. Every later schema change is a new numbered migration, never a baseline edit. After the migrations and before serving, `compactDatabase` (`compaction.ts`, compact-observation-detail D7) converts a database still in `auto_vacuum = NONE` to incremental mode with one `VACUUM` outside any transaction (`db_compacted` with page counts and duration); a failure is logged as `db_compaction_failed`, keeps the previous mode and every row, never stops the start, and is retried at the next start; a new, empty file takes incremental mode before its first table (`startIncremental`) and needs no `VACUUM`. The observation service runs `PRAGMA incremental_vacuum` after each prune pass, so freed pages leave the file and therefore its backups. `DatabaseBackups` (`backups.ts`) copies with `serialize()` on the server's own connection outside any transaction (retried up to 3 times), writes `<name>.partial`, fsyncs, renames to `backups/<stem>-<UTC stamp>-<reason>.db`, and runs `integrity_check` over a separate read-only connection, renaming a failing copy `.corrupt` (logged, kept in `status()` failures, out of rotation); the hourly `interval` snapshot is skipped while `total_changes()` equals the last snapshot's stored value. Rotation (`backupFiles.ts`, at startup and after each snapshot) keeps 24 `interval`, 7 `startup`, every backup of the newest 3 migrations, and the newest 3 `.corrupt` and 3 `.partial` (never the one being written); other files in `backups/` are never touched. In-memory databases take no backups. Backups stay on the host; the restore procedure and what it does not bring back are in `docs/operations/database-backups.md`.

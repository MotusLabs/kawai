# Plan execution

Execution, integration landing, promotion, holds, and pause. Part of [the architecture reference](README.md).

- Plan execution (plan-execution, `src/server/plans/execution/` and `src/server/plans/landing/`): the human Starts an approved plan's revision from the Plans view after eleven ordered preconditions pass (plan open, revision current, validation current, start conditions resolved, strategy impact, one execution per plan, changes unclaimed, artifacts on the base branch, roles routable, landing ready — a read-only probe of git, the GitHub origin, gh auth, write permission, the default branch, the floor map, and change names — and the landing mode registered). Start records its snapshot (floor map, parallel limit, merge method, base head) as migration 8's rows: one execution, one change row per change. The executor (`executor.ts`) is a single-flight tick loop per team: the pure `planSteps` planner schedules changes (a dependency waits until its dependency lands; the parallel limit holds back ready ones; stopped dependencies hold dependents), provisions worktrees from origin's base (never forced, reusing an earlier execution of the plan's worktree and branch, stopping as name-taken otherwise), creates Kawai's task per change with the attempt's immutable manifest, and drives rounds — each result a round that is pushed without force, given the change's one pull request, CI-read with one rerun (flaky passes don't cost a round; three failed fix rounds stop the change as round-limit), reviewed by an independent claimant (an author claiming its own review stops it as review-unavailable), and landed one at a time per team through a landing slot: brought up to date with the base (a clean GitHub update carries the round onto the new head; a conflict returns the change as an update attempt naming the files), merged with the reviewed head pinned, and recorded as a landing fact with the tree check. One composition runs it all: `composeExecutionCore` builds the store, the real ownership, and the wake hub before the team services (they take the ownership, so production has no NULL_OWNERSHIP), and `composePlanServices` — given the team services — constructs the executor with the real adapters and the `ExecutionRuntime` (`executionRuntime.ts`): boot runs D14 recovery to its end, clears orphan landing slots, installs the D5 wakes (a committed command; task rows, result/finding writes, and mail of owned tasks only; every archive, member release included; the 60 s timer, 1 s under the development fixture), then wakes the running teams; shutdown unbinds the wakes and closes the executor; under the fixture switch the deterministic fixture adapters (`fixtureAdapters.ts`) replace the gh surface and probe and the settings carry the fixture floor. Kawai is the system actor behind all of it — task creator, dispatcher, sender, and acceptor — and while an execution owns a change only Kawai dispatches its task, hands off, or releases its worktree; results for it must carry a commit on the change's branch; replies to Kawai's instruction mail are refused with guidance; no tool starts, stops, retries, or approves an execution. The human commands (Start preview, Start, Stop, Retry) go over the chat WebSocket (`team-plan-execution-*`, answered by `team-plan-result`) — the Start dialog sends the preview as it opens and renders the server's standing, Start armed only while it reads ready — and every execution write re-pushes the plan's detail with each change's state, waiting reason, round, PR, and landing fact. Routing honors the plan's roles: instruction mail carries the role's `allowed_profiles` (members outside them are excluded with the outside-role reason, spawn slots offered only for allowed profiles, `profile-order` by the role's order) and review handoffs carry `author-profile:<id>` tags so a rule can route the review away from the author's model; a forward keeps the list without the limited profile. Settings are user-level only: `~/.kawai/teams.json` takes a top-level `planExecution` default and per-team overrides — `floorChecks` (the four CI floor checks mapped to check names; no default, so Start refuses without one), `maxParallelChanges` (default 3), and `mergeMethod` (merge, squash, or rebase) — read through `TeamCaps.planExecution` with malformed values logged and defaulted.
- Integration landing (integration-candidates D1–D8, `src/server/plans/landing/` and `landing/integration/`): landing goes through a `LandingMechanism` registry (`landingMechanisms.ts`: `probe`, `startBase`, `land`, `landOutcome`, `effectAdapter`, plus optional `startEffects`, `effectDone`, `roundFailed`) that the executor, provisioning, and Start resolve by the execution's recorded landing mode; `directMechanism.ts` is plan-execution's direct landing unchanged, and `cleanMerge.ts` holds the clean-merge check both share. A plan whose `landing` is `integration-branch` records that branch as the execution's base branch (its head on origin, or the default head while it is missing) and the default branch as the promotion target on its `plan_integration_branches` row; the probe adds four `landing-ready` rules (not the default branch, not a change name, on origin only with this plan's record, no other plan's record). A missing branch is created by the execution-level `create-integration` effect (key `<execution>::create-integration:<n>`, inserted with the execution, `gh api -X POST …/git/refs` at the default head): every waiting change holds until it is done; a 422 read back at the requested commit or under this plan's record is success, a foreign ref or three transient failures stop every waiting change as `effect-failed` (resuming `waiting` on Retry, which issues the effect again under the next `<n>`), and the done effect records the creation (a re-creation updates the creation fields). Each worktree starts from the branch's head on origin when provisioned, so a dependent sees its dependencies. The implement and fix instructions name the integration branch as the change's base and say Kawai alone writes it (never push to it); the plan note repeats it, and `plan_get` carries `integration` per branch — the target, the head Kawai last recorded, the candidate chain newest first with states and outside commits, the promotions, and the promoted `seq` (`integrationView.ts`, pure over stored rows) — while no agent tool creates, fast-forwards, or promotes an integration branch or cancels a promotion. A passed change runs direct's steps 1–3 (conditions, the slot, up to date with `update-branch` and the clean-merge check — a carried round's candidate stays `verifying` until its own CI decides, and a failed one is `failed` with the round's fix attempt), then its own step: the rewritten check against `referenceCommit` (the last landed candidate, or the creation commit), the exact candidate (the round's commit over the head it contains, with the owner's commits since the reference in `outside_json`), and the non-forced `fast-forward` effect (`gh api -X PATCH …/git/refs/heads/<branch> -F force=false`). A fast-forward that lands records, in one transaction, the candidate `landed`, the landing fact (mechanism `integration-branch`, head = merge = the candidate commit, the re-read base, tree verified, no post-merge CI) and the change `landed`, then Kawai's acceptance and completion as in direct landing; a refused one (422) or a branch moved by hand supersedes the candidate and returns the change to the up-to-date step keeping the slot, and a branch lacking the reference commit stops the change as `integration-rewritten` naming the head and the missing commit — Kawai never forces it; Retry checks again. Restart inspection: `create-integration` reads the ref (at the commit: done; missing: run again; elsewhere: foreign), `fast-forward` reads the head R (R contains C: done; C contains R: run again; else the moved/rewritten rules). Start appends `promotion-idle` (a running promotion of the plan refuses, naming it and its step) and `landings-on-base` (a landing fact the base head lacks refuses, naming the change and the branch it landed on — so a plan switched to direct before promotion cannot start). The tables are migration 13 `integration-candidates`. Under the development fixture (`fixtureIntegrationAdapters.ts`) both mechanisms probe through the fixture probe, and the integration mechanism and promotions write refs on the fixture repository's bare origin with GitHub's rules (a create refuses an existing ref and a fast-forward a non-descendant, as 422, never forced), a promotion merge writes a real two-parent merge commit, and pull requests, CI, and `gh pr close` stay the fixture registry's — nothing calls gh.
- Promotion (integration-candidates D9, D10; `src/server/plans/landing/integration/Promotion*.ts`, `promotion*.ts`): the human promotes a plan's integration branch into the default branch through `PromotionService` (human only; an agent caller is refused, and no agent tool promotes or cancels). **Promote** reads first — origin's branch head, whether the target already contains it, the repository's `allow_merge_commit` (`gh api repos/{o}/{r}`), the landing probe, and whether the next promotion branch `<branch>--promote-<n>` exists — then, in one transaction through `PlanService.recordPromotionEvent` (`promotion-started`, compared payload `branch` and `fromSha`, replayed by command id), evaluates the ordered `PROMOTE_PRECONDITIONS` (`integration-branch-known`, `no-execution`, `no-promotion`, `from-current`, `something-to-promote`, `merge-commits-allowed`, `landing-ready`, `promotion-name-free`; an unreadable value fails closed, every failing entry is named, a refusal writes nothing) and inserts the promotion pinned to `fromSha`, the last landed candidate it contains (`through_seq`), and the floor snapshot; the plan's lifecycle is untouched, so a completed or cancelled plan promotes. The preview answers the standing, the pinned head, the carried candidates, and their outside commits. The executor ticks `PromotionRunner` after the executions (the pure `planPromotionStep` decides, the runner reads and applies): create the promotion branch at `fromSha` (`create-promotion-branch`, a 422 read back), open its pull request into the target, take the team's one landing slot as holder kind `promotion` (live while running with no recorded merge; a waiting change shows the promotion branch, a waiting promotion the holding change), bring it up to date (predicted or GitHub-refused conflicts fail as `promotion-conflict` with the files; a head failing the clean-merge check as `effect-failed`), CI on the floor snapshot with one rerun (`ci-failed`, `ci-missing`, `ci-timeout`), re-read the target (a moved target returns to the up-to-date step; the third move fails as `target-moved`), merge with `--merge` whatever the team's merge method, pinned to the verified head, then record in one transaction `merge_sha`, `tree_verified`, a `promotion` candidate (`passed`), and the slot's release, fast-forward the integration branch to the verified head (the candidate `landed`; a branch moved or rewritten meanwhile is left as it is, the candidate `superseded`, with the note), and finish `merged`. Every finish — merged, a failure, or a Cancel — goes through one transaction that cancels pending and `unknown` effects, releases the slot, sets the outcome (`failed:<reason>` for failures), queues `close-pr` (`gh pr close --comment`) when a pull request exists — or `open-pr` ran without recording one, which `close-pr` then finds by its head branch — and nothing merged, and writes `promotion-finished` once under `promo:<id>:finish` (actor system). **Cancel** needs a reason (`promotion-cancelled`, compared payload `promotionId` and `reason`), is refused once the merge is recorded (naming it), finishes at once unless a merge is running or unknown — that merge settles first and, if it completed, the promotion finishes merged with a note that the cancellation came too late. Promotion effects (`promo:<id>:<kind>[:<moves>]`) run through an `EffectRunner` over `plan_promotion_effects` with D14's backoff; at startup every `running` one becomes `unknown` and is inspected (D14's table; `close-pr` reads the pull request) before anything repeats, an exhausted inspection failing the promotion as `effect-unknown`; a `close-pr` that fails after its retries leaves the outcome and notes the pull request is still open. The human's commands go over the chat WebSocket addressed by `teamPath` (`promotionConnections.ts`: `team-plan-promotion-preview`, `team-plan-promote`, `team-plan-promotion-cancel`, answered by `team-plan-result` with `promotionPreview` or `promotion` and `replayed`, or `error` with the failing entries), and every branch, candidate, promotion, or promotion-effect write re-pushes the plan's detail with `integration` (an after-commit notice from the integration and effect stores). In the Plans view, the Execution section marks a landed change **promoted** once a merged promotion carried it (`promotedChanges`), and `PlanIntegrationPanel.tsx` follows per branch: the head and target, the candidate chain newest first (`seq`, change, commit, CI, state, outside commits flagged — a failed candidate stays beside its replacement), **Promote to <target>** only while a landed change is left to promote and nothing of the plan runs (`somethingToPromote`), and the promotions newest first (`PlanPromotionRow.tsx`: step, pull request, CI on the floor snapshot with flaky marks, target moves, outcome, and **Cancel promotion…** with a required reason). `PlanPromoteDialog.tsx` asks for the preview as it opens and shows the standing, the head it pins, the carried changes, and the outside commits; Promote sends that head as `fromSha`. `teamPlanStore` keeps the detail's `detailIntegration`, the dialog previews (`promotionPreviews`), and one command id per dialog (`promote:<plan>:<branch>`, re-minted when `fromSha` changes; `cancel-promotion:<id>`); controls disable while disconnected and refusals show inline. The runtime wakes, at boot, every team with promotion work, and the executor's timer stays armed while a team has any.
- Plan holds (revision-control D4–D5, `src/server/plans/revisionControl/`): the human holds a whole plan or named changes through `HoldService` (`place`, `release`, `extend`; agent callers refused; a release wakes the executor). The pure `holdGate` is the one hold-coverage check, consulted at every step that would advance held work: the executor's `planSteps` withholds provisioning, every attempt dispatch, the review and fix handoffs, and Retry's dispatch while the change keeps its real stage, so a release resumes exactly there and each owed dispatch runs once; decisions still record under a hold — a result's round is recorded and its push, PR, and CI run, while the review handoff, the landing slot, and the merge wait. A held change holding the landing slot with no live landing-kind effect gives it up and returns to `gating` (a running merge settles; the hold applies from the next step); a running promotion reaching a held step before its merge gives up the slot and waits at step `held`, re-running its up-to-date step once released; `no-hold` is appended to `START_PRECONDITIONS` (a whole-plan hold refuses; a changes-scoped hold passes, its changes unprovisioned under the gate) and to `PROMOTE_PRECONDITIONS` (a whole-plan hold, or any held change the promotion would carry, refuses), both naming the holds.
- Plan pause (revision-control 4.3–4.5, `src/server/plans/revisionControl/`): the human pauses a plan's held changes through `PauseService.pause`; targets derive from stored rows and live holder facts. The executor's tick (`runPauseTick`) delivers the owed pause mail once (the stored `message_id` is the marker) and records Paused only through the guarded write when the work is on `origin` and the holder is release-ready. A Pausing attempt target's claimant records a checkpoint with `task_checkpoint` (clean worktree, the branch's head); Kawai pushes it as a `push-checkpoint` effect, never forced. The human resolves each target — Continue (one `plan-resume`), Adapt (publishes revision N+1 and mints one fix row), Restart (one attempt from the checkpoint) — decided once, replayed by command id, dispatched only after the hold releases; no agent tool pauses, resolves, or applies.

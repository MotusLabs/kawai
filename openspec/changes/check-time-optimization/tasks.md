## 5. Template test database (D5)

Implementation notes (branch `feat/test-db-template`, stacked on `feat/property-case-profile`):
- The database uses a rollback journal, not WAL (`db.ts`), so a closed template is already one file. `buildTemplateDatabase` (`scripts/lib/testDbTemplate.ts`) closes it and fails the run if a `-wal`, `-shm`, or `-journal` file remains. The design's "no checkpoint" mutant (5.2, V3) is equivalent here: leaving the template open survives, because committed transactions are already in the main file.
- `initDatabase` takes a `startup` snapshot on every open, including of a copy. A copy therefore writes no pre-migration backup but does write one `startup` backup. TD1 checks pre-migration backups. The spec scenario "A fresh test database" said "no backup file is written", which a test-only path cannot meet without changing production `initDatabase` (excluded by X2); it now reads "no pre-migration backup is taken", and design D5 says the same.
- 5.1: the runner builds the template in a child (`scripts/build-test-db-template.ts`, spawned through `scripts/lib/testDbTemplatePaths.ts`), so the database modules stay out of the check machinery's import closure (`escapeClosure.test.ts`). A failed build fails the run with the migration's own message (`Migration <n> (<name>) failed …`).
- 5.3 measurement: per-file migration counts come from running the 60 heaviest non-migration candidates (duration × call sites, from the timings record) under an isolated HOME and counting `pre-migration-2` backup events. On this workspace, a new-file migration took about 830 ms and a template copy about 11 ms, so each migration saves about 0.82 s. `:memory:` databases cannot be copied and stay on `initDatabase`.

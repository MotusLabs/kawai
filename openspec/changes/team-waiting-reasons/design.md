# Design

## Context

Builds on `agent-teams`/`team-tasks` (dispatcher, worktree staffing, `team_spawns` reservations) and `profile-routing` (candidates, caps, router holds, cooldowns). The dispatcher already recomputes everything a waiting reason needs on every pass: `MailRecipient` (idle, pendingRequest, available, worktree, parked, profile, cooldownUntil) in `sessionMailbox.recipient()`, the eligibility filter in `MailDispatcher.eligibleFor`, the capacity counts in `WorktreeStaffing.counts` and `buildCandidates`, the router's hold/cooling decisions, and the spawn backoff in `WorktreeStaffing.failedAt`. Passes run on session record changes — status, project path, archive, and SDK session identity via `ChatSessionManager.applyPatch` — on the driver's `request_resolved` event and asynchronous team resolution (`SessionTeams.onResolved`), on limit events, rule loads, mailbox changes, and turn ends. Two gaps break visibility: `TeamMailboxPanel.tsx`'s categories match none of the states for `spawning`, so reserved mail vanishes from the view; and the reasons are never computed or published — `team-mailbox-snapshot` carries rows and routing state, nothing else. One gap breaks correctness: after a failed spawn, `staffing.ts` requeues the mail and records `failedAt` (a 30 s per-message backoff), but nothing ever wakes the dispatcher at the backoff's end — `armTimer` arms on `nextDueAt()`, recipient cooldowns, dispatcher holds, and `wakeAt()` (only `outcomes.nextNoteAt()`), so the retry fires only when an unrelated change happens to notify.

## Goals / Non-Goals

**Goals:** every unsettled mailbox row renders with a section; every waiting row carries a server-computed reason (immediate blocker plus other constraints, with counts and named sessions) derived from the same state that makes dispatch decisions; reasons refresh when capacity or availability changes; a failed spawn retries on its own; worktree occupancy is readable as one model.

**Non-Goals:** staffing-rule changes (a manual session still never occupies a worktree for spawning; caps keep their current semantics); watching `~/.kawai/teams.json` (a changed cap applies at the next pass, as today); persisting reasons, roster, or ledger (in-memory, rebuilt by the first pass after restart); new sequenced chat events or database migrations; the Team view, attention queue, and staffing controls (`team-workspace`, Wave B2); threads and delivered history (`team-message-threads`); assignment state and accountable owners (`task-assignment`); stage gates, revision barriers, checkpoints, and safety denials (Wave C); changing the parked/uncertain rows' existing explanations (they already say why they wait; only their label texts may be shared with the new formatter).

## Decisions

### D1. Reasons are typed constraints, blocker first

`src/shared/team.ts` gains `WaitingConstraint` — `{ kind, counts?, sessionIds?, retryAt?, detail? }` with one `kind` per cause (recipient-busy, recipient-pending-request, recipient-unavailable, profile-cooling, startup-failed, no-eligible-member, group-cap `n/m`, profile-cap `n/cap`, team-spawn-cap `n/m`, worktree-occupied, spawn-backoff, routing-hold, all-profiles-cooling, group-missing, starting-agent) — and `WaitingReason = { blocker: WaitingConstraint; others: WaitingConstraint[] }`. The server sends one deterministically ordered list — a missing group definition first (nothing can proceed without it), then capacity (group cap, then per-profile cap, then team spawn cap, then worktree occupancy), then member facts (no-eligible-member, recipient states, startup-failed), then spawn and routing specifics (spawn-backoff, routing holds, all-profiles-cooling, cooldown ends) — and the first present entry is the immediate blocker; the rest are whatever else applies. One exception: a `spawning` row's blocker is always `starting-agent` — its own reservation counts toward every cap and holds the worktree, so the capacity facts it creates itself are listed in `others`, never as the blocker. Caps lead because they are the lever a human acts on (`team-workspace` later) while member busyness resolves itself, and because the doc's own examples lead with counts. The no-eligible-member breakdown (group mail only; direct mail has single-recipient `recipient-*` reasons instead) names each member's cause: busy, pending card, parked, other worktree, unavailable, startup failed, or excluded profile. When a start failure is both its own constraint and a breakdown entry, the standalone `startup-failed` kind (with its error text) is the blocker and the breakdown entry is detail. Cooling is not a group-path member exclusion — cooling members stay candidates (`buildCandidates` keeps them; the built-in strategy skipping them surfaces as the separate all-profiles-cooling constraint) — while direct mail excludes cooling recipients outright. Clients render the blocker as one line and the rest behind an expander, so the doc's "display the immediate blocker and allow expansion for the others" is a rendering rule over one payload. *Alternative:* a single human-readable string per message — rejected: the doc requires blocker-first display with expandable others, and links (named sessions, worktrees) need structure.

### D2. The decision path computes the reason, not an observer

Group mail: `ProfileRouter.route` already sees members, caps, spawn allowance, holds, and cooldowns; `RouteResult`'s `none` and `hold` gain a `diagnosis: WaitingConstraint[]` built from the same inputs (eligibility breakdown from the dispatcher's member states, counts from `buildCandidates`' live tallies, spawn facts from `spawnContext`). The decision log keeps its role (a log); reasons are not scraped from it. The dispatcher gains a member-state cause reporter over the shared `MailRecipient` fields (idle, available, pendingRequest, parked, worktree, group, team, profile, cooldown, excluded profile); `eligibleFor` and the `push` claim predicate keep their exact current boolean shapes on top of it — they check different subsets (only `push` consults `excludedProfile` and direct-mail cooling; only `eligibleFor` consults `failedThisPass` and idle order), so this is a reporter beneath unchanged predicates, not a merged predicate — and dispatcher tests pin both shapes. A reason is therefore derived from the same state the decision used, as of that pass: a snapshot, not a guarantee, since `push` re-checks after the awaited prepare/interrupt. Direct mail: the dispatcher's recipient view computes the reason (busy / pending card / unavailable with `startBlocker` text exposed by `ChatSessionManager` / profile cooling). Per-message start failures (today only `failedThisPass`, which dies with the pass) are tracked with their error text until the message leaves the queued surface — delivered, cancelled, dead-lettered, or discarded. *Alternative:* an independent explainer that re-derives state from snapshots after each pass — rejected: two derivations drift, and the drift is exactly the wrong-reason bug this change fixes.

### D3. Publication: transition-time diagnoses plus an after-pass ledger

A `spawning` row lives only inside one awaited dispatch pass: the reserve transaction (whose store notify publishes the only *guaranteed* `spawning` snapshot — a notify from an unrelated message during the awaited agent creation can also publish one, with the row still `spawning` and the reservation row already there) → awaited agent creation → delivery or requeue, so by the time any pass ends the row has left the state and no pass-end hook can diagnose it. Publication therefore has two paths. Transition-time: `starting-agent` is derived when a snapshot is assembled, from the pending `team_spawns` reservation (group, profile, worktree, elapsed since `created_at`). For that source to exist at the reserve notify itself, the reservation transaction inserts the `team_spawns` row **before** flipping the message to `spawning`, and a failed reserve throws so the transaction rolls the insert back — end state on success and failure is identical to today's reserve-then-insert (`reserveForSpawn`'s failure fires no listener, so nothing observes the rolled-back insert); only what the synchronous notify sees changes. On spawn failure, staffing records the `spawn-backoff` constraint with its retry time in the `sessionMailbox.ts` reason ledger — the single diagnosis store, written next to `failedAt` before the requeue notify publishes. After-pass: the dispatcher gains an `afterPass` hook, and the ledger is updated from the pass-computed diagnoses (cap release, cooldown end, eligibility changes) — the cases where no row state changes and today nothing re-publishes. When a team's ledger changed, its mailbox snapshot is re-sent (`mailboxConnections.publish`). The snapshot (`team-mailbox-snapshot` in `src/shared/types.ts`) gains optional `waiting: Record<messageId, WaitingReason>` and `worktrees: TeamWorktreeOccupancy[]` fields; older clients ignore them (existing precedent: the additive `routing` field). Elapsed/age rendering stays client-ticked as today; no timer-driven server refresh.

### D4. One worktree-occupancy read model

New pure `src/server/team/teamRoster.ts`: `teamRoster(teamId)` groups live (non-archived) sessions by `worktreeRootOf(projectPath)`, each entry `{ worktree, sessions: [{ sessionId, group, profile, status, spawned, taskId }], pendingSpawns: [{ group, profile }] }` (pending from `team_spawns` rows). It includes manual and spawned sessions — transparency — while staffing semantics stay unchanged: `WorktreeStaffing`'s worktree-writer count and the `worktree-occupied` reason read the roster (manual sessions listed but not counted as writers), so the name shown as occupant is the same fact that blocked the spawn. Cap arithmetic (group `max`, per-profile caps, team spawn cap) stays in `staffing`/`candidates`, which already count pending reservations. The roster rides the mailbox snapshot (D3) so the later `team-workspace` view and `task-assignment` dispatch preview can reuse it without a second source.

### D5. The failed-spawn backoff wakes the dispatcher

`WorktreeStaffing` exposes `nextRetryAt(): number | null` (min unexpired `failedAt + RETRY_AFTER_MS`). `sessionMailbox.ts` folds it into the dispatcher's `wakeAt` (min with `outcomes.nextNoteAt()`); `armTimer` already arms on `wakeAt`. No polling, no new timer source: the existing minimum-wins timer simply learns one more time. The `spawn-backoff` constraint's `retryAt` is that same timestamp, so what the UI shows as "retry at" is the time the retry will actually run. `failedAt` entries are cleared not only on a successful spawn but whenever their message leaves the queued surface (delivered, cancelled, dead-lettered, discarded) — the same lifetime as the start-failure tracker (D2) — so `nextRetryAt()`, which the timer re-reads on every re-arm, never scans a stale backoff.

### D6. Dead-letter labels are a shared code map

`waitingLabels.ts` (client) maps known reason codes (`worktree-missing`, `killed-recipient`, `killed-sender-without-group`, `hop-limit`) to readable text, falling back to the raw string; the raw code stays visible. Unknown codes render verbatim, so future codes degrade gracefully instead of lying.

### D7. Scope of states that carry reasons

Reasons apply to `queued` (due now), `awaiting-request`, and `spawning`. `queued` with a future `deliverAt` keeps its "Due …" line (nothing blocks it); `claimed` is Receiving; `parked`, `uncertain`, `dead` keep their existing explanations, and `dead` additionally gets D6 labels. This is the entire unsettled surface — no state is left without a section once `spawning` renders as Starting agent.

## Risks / Trade-offs

- [Reason churn floods snapshots] → publish only when a team's ledger actually changed (structural compare, not timestamps); counts and names change rarely while mail waits.
- [Cause reporter changes dispatch behavior] → it sits beneath `eligibleFor` and the `push` claim predicate, which keep their exact current boolean shapes; dispatcher tests pin both shapes, delivery order, and claims.
- [Roster in every snapshot grows payload] → teams are small (single-digit sessions); the roster is flat and bounded by live sessions plus reservations.
- [`startBlocker` becomes public API] → exposed as a read-only accessor returning the existing refusal text; no behavior change to `available`, which keeps calling it.
- [Start-failure memory lost on restart] → accepted (non-goal: persistence); after restart the first pass recomputes everything it can, and a still-failing spawn re-records its failure.

## Migration Plan

None. Additive optional snapshot fields; in-memory ledger, roster, and diagnosis state; one dispatcher hook; one staffing accessor. No tables, columns, or new sequenced events.

## Open Questions

All three were decided by the human on 2026-10-13; none remain open.

- **Q1 — constraint ordering when several apply** (e.g. no eligible member *and* group cap reached). *Decided: caps-first* — capacity constraints (group cap, then per-profile, then team-spawn, then worktree-occupied) rank before member facts, then spawn/routing specifics, deterministically within each band; the first entry is the immediate blocker. Rationale: the spec's multi-constraint scenario already asserts it, the human's plan leads with "group cap 2/2", and the cap is the actionable lever (`team-workspace` later) while member busyness resolves itself. Recorded in D1.
- **Q2 — controls on a Starting agent row.** Today `spawning` rows have no controls (they match no category). *Decided: none in this change*; cancelling a live spawn reservation stays a staffing control for `team-workspace` (Wave B2). Cancel/Retry/Discard/Hand off remain exactly as today.
- **Q3 — roster payload placement.** *Decided: carry `worktrees` on every `team-mailbox-snapshot`* (small, always fresh, no new message type). The rejected alternative — only while a Mailbox panel is open — saves bytes but makes the later Team view need a second subscription.

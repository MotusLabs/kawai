# Design

## Context

Builds on `agent-teams` (durable `team_messages`, dispatcher, atomic claims), `team-tasks` (task mail, task context at delivery, `TaskActor` with `kind: 'human'`), and `profile-routing` (parked/forwarded states and their `team_messages` columns). The mailbox panel (`TeamMailboxPanel.tsx`) is a delivery-operations surface: `MailboxStore.listForTeam` returns only unsettled rows, so delivered mail vanishes from every view the moment it settles, and `MailboxStore.retry` rewrites an uncertain row in place — clearing `claimed_by`, `reason`, and `pushed_at` — while `requeue` drops the claim and push facts and `release` those plus the delivery, park, and claim-commit facts, so what happened to a message is overwritten rather than retained. Peer rows (`ChatMessages.tsx`) label senders by raw session id, and a killed session's `chat_sessions` row is gone, so even the id's name is unrecoverable (`teamTaskLabels.sessionLabel` renders `<id> (gone)`).

Sessions already carry `name` and `nameSource` (`db.ts`); task mail already carries a task context built at push time (`dispatcher.ts` → `taskContext`); `ChatConnections.ts` already pushes toast notices for dead letters. Wave B1 siblings: `team-waiting-reasons` renders waiting reasons on pending rows (rendered here only if present), `task-assignment` owns assignment state; Wave B2's `team-workspace` mounts a full-page Team view and `task-revision-publication` separates delivered from acknowledged revisions.

## Goals / Non-Goals

**Goals:** delivered history and pending mail in one filterable, paged, live view; a thread view that survives its participants (including killed sessions); an append-only record of what happened to each message; the human able to send and reply to team mail with honest urgent semantics.

**Non-Goals:** full-page Team view, attention queue, mobile/keyboard list-detail navigation (`team-workspace`); delivered-vs-acknowledged revision states and revision re-notification (`task-revision-publication`); waiting reasons on pending rows (`team-waiting-reasons`); assignment state or accountable owners (`task-assignment`); presenting receipt as accepted work — delivery state is not acceptance; results and acceptance (UX doc §5) own that in the later results-and-review changes; agent-initiated mail to the human beyond replies in human-started threads; read/unread state or an inbox for the human; full-text search of bodies; retroactive history for messages created before this change (their rows show timestamps only); human-scheduled mail (the composer sends immediately; agents keep `schedule_message`).

## Decisions

### D1. One read model over the durable rows, not a projection
The Messages view reads `team_messages` directly (new `messageQuery.ts`: filters, paging, thread and task subsets) exactly as the mailbox panel reads `listForTeam` today. No separate delivered-mail table or in-memory index: the rows the dispatcher writes are the history. Paging is keyset-style over `created_at, rowid` (the order `MailboxStore.select` already uses), newest first for the list view. *Alternative:* a projection table refreshed on change — rejected: a second copy of the same rows invites drift and doubles migration surface.

### D2. `team_message_events` is append-only and written inside the transitions
A new `team_message_events` table (message id, team, seq within the message, timestamp, event kind, actor, and the facts the change overwrote: previous state, claimant, recipient, reason). Recording happens inside `MailboxStore`'s transition helpers (`enqueue`, `claim`, `markPushed`, `markDelivered`, `requeue`, `holdUncertain`, `retry`, `cancel`, `discard`, `park`/`unpark`, `release`, `markForwarded`, `reserveForSpawn`, `holdForRequest`, `deadLetter`), so no state change can escape logging — the same single-writer discipline the state transitions already have. This is what makes E11's retained retry/discard/cancel history possible: today `retry` clears the very fields that would explain the hold. Events are durable rows; they survive restart with the messages they describe. *Alternative:* reconstruct history from row fields — impossible after the overwrites above. *Alternative:* log only human actions — rejected: spawn reservations, parks, and dead letters are exactly the system actions a handoff investigation needs.

### D3. `team_session_directory` keeps names past kill
A small table keyed `(team_id, session_id)` holding the last known name and group, upserted by `ChatSessionManager` when a session is created or renamed (`nameSource` already funnels renames through `updateSession`). While the session lives, `chat_sessions` is authoritative; the directory only answers after kill. Views resolve a participant through live sessions first, directory second, and render `Name (gone)` — matching the existing `(gone)` convention — with ids in expandable metadata. Clicking opens the chat only for live or archived sessions (both have rows and transcripts); killed participants show the label and no link. `taskStore.summary`'s participants query gains `from_session IS NOT NULL` so human senders do not surface as null participants.

### D4. The human is a first-class actor, mirroring `TaskActor`
`from_kind` ('session' | 'human') with nullable `from_session`, and `to_kind` gains 'human' with nullable `to_id` — the same shape `team_tasks` uses for creators (`TaskActor` becomes an alias of the shared `TeamActor`), and `TeamMessage` widens to match (`toKind: 'group' | 'session' | 'human'`, nullable `toId`/`fromSession`). SQLite cannot relax NOT NULL with `ALTER TABLE`, so migration is one guarded rebuild of `team_messages`: create-copy-drop-rename inside a transaction, skipped when the columns are already nullable — the same check-then-migrate pattern as `migrateTable`, just heavier. The rebuild must create all five indexes on the copy itself — `team_messages_queue`, `team_messages_thread`, `team_messages_recipient`, `team_messages_claimant` (from `CREATE_TABLE_SQL`) and `team_messages_task` (created in `migrateTable`) — because the constructor runs `CREATE_TABLE_SQL` before `migrateTable`, so the DDL block's `CREATE INDEX IF NOT EXISTS` statements have already executed and will not run again for the rebuilt table. `mapRow` widens with them (`to_kind === 'human'`, null-safe `toId`/`fromSession` through the existing `text()` helper — never `String(null)`), and every existing delivery query matches `to_kind = 'session'` or a live recipient id, so human-directed rows never enter the dispatcher by construction. The envelope gains `senderKind` and a nullable `senderSession`; `parseEnvelope` treats a missing `senderKind` as 'session', so recorded transcripts keep parsing.

### D5. Human-directed mail is settled on send
An agent's reply to human-originated mail goes to `to_kind: 'human'`: there is no agent session to claim or push it, so the row is recorded as delivered immediately (sender: the replying agent, recipient: human) and every connected client of the team gets a toast through the existing notice path in `ChatConnections.ts` (`broadcastMailboxNotice`, else every connection subscribed to the team's sessions — the `team-mailbox-dead-letter` pattern). The message lands in its thread like any other. Agents still cannot *start* mail to the human: `send_message`/`schedule_message` refuse a `human` recipient; only `reply` on a human-sent message can target the human. This keeps the human's composer the sole initiator of human-visible threads while not dead-ending them.

### D6. `task_revision` is written at push time
The dispatcher already builds the task context at push (`taskContext(message.taskId)`); it now records that context's revision on the row in the same step. Thread detail then shows "carried revision N at delivery" from the row — a fact about the past that the current task revision must not rewrite. Wave B2's `task-revision-publication` builds its delivered-vs-acknowledged states on this column; recording it here is the boundary between the two changes.

### D7. The view is host-agnostic; the side panel is its first host
`TeamMessagesView` renders the list, filters, thread detail, and composer knowing only the shared types; `TeamMessagesPanel` mounts it in the chat side slot behind a **Messages** header toggle beside Debug, Mailbox, and Tasks (`ChatView.tsx`'s one-at-a-time pattern). The Mailbox panel is untouched: routing decisions, parked hand-off, and delivery operations stay there; the Messages view is read-plus-compose. `team-workspace` (Wave B2) mounts the same component full-page. Task detail's Messages section switches to the same rows with a fixed task filter, gaining named participants and thread links.

### D8. Wire protocol follows the established snapshot/push and request/result patterns
`team-messages-open/close` subscribe per chat session (team resolved like `mailboxConnections.ts` resolves it); the server answers `team-messages-snapshot` and pushes `team-messages` on change, re-snapshotting on reconnect (the authoritative-snapshot discipline of team-tasks). `team-thread-open` fetches one thread with its events. Human sends and replies go as `team-message-send` carrying a client `requestId`, answered by `team-message-send-result` (the task-action pattern) so the composer can clear, disable while pending, and surface refusal errors inline. Request ids live on the wire only — never in the durable rows.

## Open Questions

1. **Agent replies reaching the human** (D5): the plan excludes agent-initiated mail to the human; this change allows an agent's `reply` in a human-started thread to reach the human as a toast plus a thread row. *Recommended default:* keep it — a thread the human can never get an answer in is broken, and `reply` cannot start new threads to the human.
2. **Should the directory also re-label the task UI's `(gone)` participants today?** *Recommended default:* no — task participants keep current behavior; only message rows and peer labels adopt directory naming here, leaving a conscious follow-up for `team-workspace`.
3. **Human composer scheduling** — *Recommended default:* out of scope now (stated as a non-goal); add only if the human asks for delayed nudges.

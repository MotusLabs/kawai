## 3. Assignment service: dispatch, idempotency, reassignment, preview

- [ ] 3.1 Implement `AssignmentService.dispatch` per design D3: same-team task, catalog-valid group or live same-team non-archived session target, non-empty instruction, then one transaction inserting the assignment row and enqueueing the human-originated instruction mail (normal priority, `task_id` set, task header at delivery); verify service tests cover group and session targets, empty instruction refused with nothing written, unknown group / other-team or archived session refused, and the committed pair (assignment + mail) always appearing together.
- [ ] 3.2 Implement request-key idempotency end to end (design D4): `team-task-create` accepts a `requestKey` returning the prior task for a same-payload replay; dispatch replays return the prior assignment; different payload under a key is refused naming the differing field; "Create and assign" runs create-then-dispatch under one client key so a dispatch refusal leaves the committed task and the client draft; verify service tests cover double create, double dispatch, reconnect-style replay after success, create-ok-dispatch-failed then successful retry on the same task, and no duplicate mail in every replay path.
- [ ] 3.3 Implement reassignment per design D7: dispatch onto an outstanding assignment refuses without `handling` and names the outstanding target/state; `stop` supersedes and cancels only queued/spawning instruction mail (claimed or delivered mail untouched, recipient session untouched); `notify` supersedes and sends the previous claimed agent a normal direct note, degrading to plain supersede with no claim; every supersession journals; verify service tests cover each choice, undelivered vs delivered old instructions, notify-without-claim, and supersession history retention.
- [ ] 3.4 Add the read-only dispatch preview (design D6): target worktree resolution, role, effective profile (session target's profile, or the spawn profile a group's strategy/caps would pick via a pure helper over the staffing counts — never a reservation), approval policy, staffing availability, and a worktree-mismatch warning for session targets; verify preview tests cover group-with-worktree (idle member vs spawn-blocked vs spawn-allowed), session targets, cooling/absent profiles, and that preview performs no writes and no spawn reservations.
- [ ] 3.5 Document assignment records, dispatch idempotency, retry, reassignment semantics, and preview in the How It Works section, including that dispatch never changes task status and never creates a worktree; verify documented rules match the service tests.

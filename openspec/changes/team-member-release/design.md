# Design

## Context

- Spawned members are `chat_sessions` rows with `spawned = 1` and the `task_id` they were spawned for; `associateTask` never rewrites a spawned member's task (`ChatSessionManager.ts`), so "the members spawned for task T" is a stable query.
- Every staffing count treats any non-archived member as live (`staffing.ts` `counts`, `sessionMailbox.ts` `members`). Archiving is therefore the whole capacity mechanism; nothing else needs to change for a release to free slots.
- `ChatSessionManager.archive` already does the safe stop: interrupt, kill the process, settle recipient claims (`settleRecipient`), clear activity/notices, persist context usage, set `archived_at`. `applyPatch` notifies the dispatcher on status, path, and archive changes; `request_resolved` and mailbox changes notify it too. A dispatch pass therefore follows every event that can make a member ready.
- Task status changes go through `TaskService.setStatus` (agent tools and human WebSocket action alike) and `TaskStore` publishes every change to subscribers.
- Worktree scoping is one function, `targetWorktree(message)` in `sessionMailbox.ts`, shared by the dispatcher (`inWorktree`), router, staffing (`spawnContext` returns null when it is null), and limit outcomes. Returning null means "any member, no spawn".
- Journal authors are stored as `author_kind TEXT` + `author_session`; `TaskActor` is `human | agent`.

## Goals / Non-Goals

**Goals:** a single release primitive (readiness check + archive + journal) used by both the task-close trigger and the agent tool; no new process lifecycle (release = archive); per-group opt-outs read from the current group file.

**Non-Goals:** UI for pending releases beyond the journal entry and the existing Archive pane; changing who may close tasks; worktree or branch cleanup.

## Decisions

**D1 — Pending releases are rows, written at the close transition.** A new `team_member_releases` table (`session_id` PK, `task_id`, `team_id`, `reason`, `requested_by_kind`, `requested_by_session`, `requested_at`) is filled in the same transaction that sets the task to `done`/`cancelled`, for each live spawned member of that task whose group does not opt out. A status change out of `done`/`cancelled` deletes the task's rows. Archiving or killing the session by any path, and a human restore, delete the session's row.
*Why edge-triggered rows over a level rule ("spawned, live, task closed ⇒ archive"):* the level rule would immediately re-archive a member the human restored on purpose, and it would retroactively archive members of tasks closed before this change. Rows make restore and reopen simple cancellations and survive restart without recomputation.
*Group opt-out read at close time and again at release time* (the current file wins; a group that opts out after the close keeps its member).
*Spawns in flight at the close.* A `team_spawns` reservation and its `spawning` message are not a session row, so the close transaction cannot mark them. Two rules close the gap. First, the close transaction dead-letters the task's `spawning` mail as `task-closed` (D8); `claimSpawned` only accepts a `spawning` row, so the new session never receives it, and staffing deletes the reservation when the spawn finishes or fails, as it does today (a failed spawn's `requeue` no longer matches the dead row). Second, when a session is created spawned for a task that is already `done` or `cancelled`, the creation writes its `team_member_releases` row (group opt-out honored, `requested_by` = the task's closer from the latest status journal entry, else system). It then has no mail, becomes ready once its agent idles, and is released, freeing the worktree slot.

**D2 — Release runs inside the dispatch cycle, before routing.** `MemberRelease.evaluate()` runs from the dispatcher's `beginCycle` hook. For each pending row it checks readiness and, if ready, archives through an injected `archive(sessionId)` (the manager's existing method), appends the journal entry, and deletes the row. Running before routing lets the freed capacity serve mail in the same pass; the archive's own `applyPatch` notification queues one more pass, which is harmless.
*Alternative considered:* a separate timer or per-event hooks. Rejected: the dispatcher is already notified by every event that changes readiness (status, request resolution, mail changes, archive), so a second scheduler would duplicate that wiring. A task closing must notify the dispatcher too; `SessionMailbox` subscribes to task changes for that. So must a worker roster change (D3's worker condition): the manager's `onWorkers` sink notifies the dispatcher when a session with a pending release loses its last live worker, since no status change follows a worker that ends while the session is already idle.

**D3 — Readiness reuses the dispatcher's recipient view plus mail and worker facts.** This is the single release-readiness definition: the task-close trigger, `release_member` (D6), and `task-results-handoffs`' Release-and-hand-off all use it and add no conditions of their own. Ready ⇔ `recipient.idle && !recipient.pendingRequest` (the same `MailRecipient` the dispatcher builds), no live background worker (`ChatSessionManager.getWorkers(id)` has no entry with `live: true` — `MailRecipient.idle` is only `status === 'waiting'`, and a background worker keeps running, and writing to the worktree, after the turn that started it ends), `store.claimsFor(id)` is empty (no claimed or pushed-unsettled mail), `store.parkedBy(id)` is empty, and no `queued` direct mail addressed to the session is due. Unavailable members (missing directory, start blocker) count as ready — they hold capacity but can do nothing. Parked work is not released implicitly: the human can Hand off or discard it, after which release proceeds.

**D4 — `system` journal author, separate from `TaskActor`.** `TaskJournalEntry.author` becomes `JournalAuthor = TaskActor | { kind: 'system'; sessionId: null }`; creators and revision authors stay `TaskActor`. Stored as `author_kind = 'system'` (TEXT, no migration). The client renders it as "Kawai". Participants derivation skips system authors. Entry text: `Released <name> (<session id>): task <status> by <actor>.` or `Released <name> (<id>) at the request of <agent name> (<id>): <reason>.`
*Why not widen `TaskActor`:* `team-message-threads` re-types `TaskActor` as an alias of its `TeamActor`; keeping the journal-only kind separate avoids a merge conflict and keeps "a task's creator is never the system" true by type.

**D5 — `worktreeScoped: false` makes `targetWorktree` return null for that group.** `targetWorktree(message)` gains the receiving group's definition: when the message is group mail and the group's current file sets `worktreeScoped: false`, it returns null. Every consumer (dispatcher eligibility, router candidates, staffing spawn context, limit outcomes) then treats the mail as unscoped and never spawns for it. `targetWorktree` stays synchronous; its group definitions come from a per-cycle map filled before anything reads it. The router's `groupOf` (`sessionMailbox.ts`) is async — with no live team member it loads the catalog from the message's origin — and `beginCycle` clears the catalog cache, so the cycle start runs in this order: (1) clear the catalog cache; (2) await the definitions of every group with queued, awaiting-request, or spawning group mail, and of every group with a pending release (D1's opt-out re-check), through the same lookup `groupOf` uses, into the per-cycle map; (3) `MemberRelease.evaluate()` (D2), including D8's dead-lettering of closed tasks' waiting mail; (4) route. `beginCycle` therefore becomes async and the dispatcher awaits it before its first routing step; mail that arrives mid-cycle waits for the next cycle, as it does today.
*Missing definition:* when the receiving group's definition cannot be resolved (file deleted or invalid), `targetWorktree` returns the task's worktree — scoped, the default — so the mail keeps today's behavior: it waits for a member in that worktree, and staffing, which needs the definition to spawn, spawns nothing. Treating it as unscoped would hand a vanished group's worktree work to whoever is idle.
*Alternative considered:* lifting scoping for every killed-sender reply fallback (`attachThread`). Rejected: when a dev is killed, a reply falling back to `devs` should stay in the dev's worktree so a fresh dev is spawned there, not handed to a dev working elsewhere. The opt-out puts the choice with the receiving group, which is where the "my members never live in task worktrees" fact belongs.

**D6 — `release_member` is a `kawai-team` tool, gated at call time.** Input `{ session_id, reason? }`. The caller's group's current file must set `canReleaseMembers: true`; the target must be a live, spawned session of the caller's team, not the caller, and ready per D3. Otherwise the tool throws with a specific reason (not permitted / not spawned / other team / archived or unknown / busy / awaiting a request / live background worker / holds mail). Success archives synchronously and journals on the target's task (if it has one). Added to `TEAM_ALLOWED_TOOLS` like the other team tools. `teamPrompt.ts` describes the tool only to permitted groups. No `restore` or `kill` tool is added.
*Refuse, not defer:* an agent needs a definite answer; a deferred release would hide work the agent thinks is gone (UX doc E08 asks for an actionable refusal).

**D7 — Group file keys.** `releaseOnTaskClose` (default true), `worktreeScoped` (default true), `canReleaseMembers` (default false): strict `true|false`, invalid values reject the file like `canCreateTasks`. Existing kawai group files with these keys are already accepted today (unknown keys are ignored), so repositories can add them before the change ships.

**D8 — A closed task's undelivered worktree mail is dead-lettered `task-closed`.** Without this, a done task's instruction still queued for a worktree-scoped group (or requeued from an unpushed claim) would be delivered later or spawn a fresh dev into the task's worktree. The rule, one mail action and nothing else: group mail carrying the task's id, addressed to a group that is worktree-scoped (D5; a missing definition counts as scoped), in state `queued`, `awaiting-request`, or `spawning`, is dead-lettered with reason `task-closed` (`MailboxStore.deadLetter`, actor `system`). It runs in the close transaction for mail already waiting, and in the dispatcher, before claim or spawn, for such mail that arrives or is requeued after the close. Direct mail and mail to unscoped groups are untouched: a closing note to the dev is still delivered (and restores it if released), and a dev's report to an unscoped `lead` still arrives. Reopening the task does not revive dead letters; the human retries them from the Mailbox or dispatches anew.
*Why dead-letter, not the existing cancel:* `MailboxStore.cancel` is the human's action — it records actor `human`, and accepts only `queued`/`awaiting-request`, so a `spawning` row (D1) would escape it. A dead letter is the system's own settlement, carries a reason the Mailbox shows, and stays retryable. Assignment state is not specified here: `task-assignment` D5 derives it from the mail, so a dead-lettered instruction reads as `failed` with reason `task-closed`.
*Release never requeues a closed task's work:* `settleRecipient`, run by archive, requeues only unpushed claims, and readiness (D3) requires no claims, so a release path archives a member with none. The same holds for `release_member` on a member of an open task: a claimant with an unsettled claim is refused as holding mail; a member whose instruction was already delivered can be released, and its delivered mail and the task's assignment stay as they are, for the human to reassign. `release_member` takes no mail action of its own.

## Risks / Trade-offs

- [A dev is released while the lead still wants to send it follow-up work] → The lead can send direct mail, which restores an archived recipient; the journal entry says who was released. Groups can opt out with `releaseOnTaskClose: false`.
- [Release archives a member mid-way through uncommitted work after a human closes a task by mistake] → Release waits for the turn to end and never touches the worktree; reopen before the turn ends cancels it, and Restore resumes the same conversation afterwards.
- [`worktreeScoped: false` on a group that does spawn removes its spawning] → Documented: unscoped groups are staffed by humans; the default is unchanged.
- [A member that never becomes ready (stuck pending request) keeps its pending row forever] → The row is visible through the journal's absence and the member's needs-attention badge; the human resolves the request or archives by hand, which deletes the row (D1).
- [Re-entrant dispatch passes after each archive] → Bounded by the number of pending releases; each archive removes its row before notifying.

## Migration Plan

Additive table and frontmatter keys; no backfill (tasks already closed are not released — a non-goal). Rollback: older code ignores the table and the new keys, and reads `author_kind = 'system'` journal rows through its two-kind mapper, `actor()` in `taskStore.ts`, which coerces any kind other than `agent` (with a session) to `{ kind: 'human', sessionId: null }` — it does not throw, so an un-cleaned rollback still works but shows every release entry as written by the human. That misattribution is a false audit record, so the rollback deletes the `system` journal rows first (`DELETE FROM team_task_journal WHERE author_kind = 'system'`); they only record releases, which stay visible as archived sessions in the Archive pane. This is the one sanctioned exception to the journal's append-only rule, done by the operator outside kawai.

# Proposal

## Why

Every edit to a task's direction or acceptance is a published revision the moment it is saved (`TaskService.amend` → `TaskStore.amend`, from both the agent tool `task_amend` and the UI's `team-task-amend`). The human cannot work on a change of direction without it reaching any agent whose task mail is delivered next, and when they do mean to change direction, nothing tells the executing agent: it learns only if some later task mail happens to carry the new header. Kawai also cannot say whether an agent has *read* the new revision — a confirmed delivery is a receipt, not an acknowledgement. The approved product strategy (revision 2, P2/P3) makes owner overrides forward fixes that never block execution; that only works if a change of direction reaches executing agents deliberately and traceably. This is the baseline P2 "Publish revision with notification and acknowledgement" (UX doc §7, acceptance test E09).

Builds on `team-tasks` (immutable `team_task_revisions`), `team-message-threads` (revision-at-push in `team_messages.task_revision`, append-only `team_message_events`, the human mail actor), and `task-assignment` (the `team_task_assignments` record, its outstanding assignment and claimed agent, and the request-key idempotency pattern). It is sequenced after `task-assignment`.

## What Changes

- **Save draft.** The human edits direction, acceptance, and a rationale as a per-task draft based on a named revision. A draft is not a revision: it never changes the task's direction, never appears in a delivered task header, `task_get`, or `task_list`, sends no mail, interrupts nobody, and has no acknowledgement state.
- **Publish revision.** Publishing records the next immutable revision with its rationale, author, time, and publication command identity. It is refused as stale when another revision was published since the draft's base, so one intent increments the revision exactly once; the same command replayed returns the prior revision.
- **Publish and notify.** Publication additionally sends each affected executor — the claimed agent of the task's outstanding assignment — a direct, normal-priority revision notice bound to that assignment and the published revision, written in the same transaction as the revision. Group mail is never used for a notice; a group assignment not yet claimed needs none, because its queued instruction carries the latest revision when delivered.
- **Notify later and retry.** **Notify** on a published revision (and **Retry notification** after a failed notice) sends notices to recipients that have not yet received that revision, under a stable command key. It never creates a revision; a replay never sends a second notice.
- **Publication detail.** Each published revision shows rationale, author, and per recipient: Not notified, Queued, Delivered, Failed (with reason), Uncertain, and the Acknowledged revision — kept separate, because receipt is not acknowledgement.
- **Acknowledgement.** A new `kawai-team` tool, `task_acknowledge(task_id, revision)`, lets an agent state which published revision it is now working from. Acknowledgement is per session: a replacement claimant (reassignment, requeue to another member, forwarded work) starts unacknowledged and must acknowledge current inputs. The team prompt's task note explains when to call it; revision notices say so in their body.
- **Agents.** `task_amend` keeps its creator-only right and publishes immediately as before; it gains an optional `rationale` and an optional `notify` (publish and notify). Agents get no draft tool.
- **Historical rows.** Delivered peer rows and thread rows keep the revision recorded at delivery (`task_revision`); publication never rewrites them.
- **Revision event for results.** Every publication records a durable, ordered "revision published" fact: the `team_task_revisions` row, with `team_tasks.revision` naming the current one. Consumers compare against those rows — `task-results-handoffs` derives Needs re-evaluation at read time from a result's recorded revision versus the task's current one (that label and rule are owned there). An in-process notification after commit is offered as an optional convenience; no consumer depends on it.

Non-goals (Wave C `revision-control`): Impact Holds; checkpoints; writer stop, fencing, or lease epochs; revision barriers on submission, integration, acceptance, or archive; Pause / Continue / Adapt / Restart; compatibility classification, materiality, or affected-scope decisions across a Plan graph; urgent (interrupting) revision notices. Also out: results, acceptance, and Needs re-evaluation (`task-results-handoffs`); the Team view and attention queue (`team-workspace`); agent drafts; strategy revisions (`product-strategy` keeps its own draft/approve flow).

## Capabilities

### New Capabilities

- `task-revision-publication`: task direction drafts, publication with rationale and idempotent command identity, assignment-bound revision notices with notify-later and retry, per-recipient Queued/Delivered/Acknowledged publication detail, the `task_acknowledge` tool and replacement acknowledgement, and the revision-published fact for downstream consumers.

### Modified Capabilities

- `team-tasks`: "Only the creator or the human amends direction" — a change of direction becomes a revision only when published; the human's drafts are not revisions; creator rights unchanged. "Tasks are inspectable in the UI" — the task detail edits a draft and offers Save draft / Publish revision / Publish and notify instead of a direct amend, and revisions show their rationale.

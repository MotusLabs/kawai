# AGENTS.md

- Bun 1.x, TypeScript 5.x, React 18, Hono, xterm.js, Zustand, Tailwind.

## Commands

```
bun run dev        # frontend + backend
bun run build      # production build
bun run lint       # oxlint
bun run typecheck  # tsc --noEmit
bun run test       # unit tests
```

Run `bun run lint && bun run typecheck && bun run test` after changes.

## How It Works

- Single tmux session (default: `agentboard`) with one window per project
- Backend discovers windows, streams terminal output via WebSocket
- Parses Claude/Codex JSONL logs from `~/.claude/projects/` and `~/.codex/sessions/` for status
- Status: unknown -> working -> waiting (derived from log events)
- Notification sounds: the Permission sound plays for any known session entering `permission`; the Idle sound plays on `working` -> `waiting`, except for the selected session while the page is visible (the chat the user is already watching). Both rules live in the pure `decideTransitionSounds` (`src/client/utils/soundTransitions.ts`), applied by the `sessions` and `session-update` handlers in `src/client/protocol/sessionMessages.ts`.
- Chat sessions use the Claude Agent SDK without tmux, driving a separately installed Claude Code executable (`KAWAI_CLAUDE_PATH` or `claude` on the server PATH; version-checked against the SDK-pinned baseline 2.1.289 before creation — the SDK's platform CLI packages are stubbed out of the install, so Claude Code must be installed on the host). Turns and pending approvals/questions determine status directly. WebSocket snapshots restore history and pending requests on reconnect; SQLite rows and SDK transcripts allow restart/resume.
- The chat agent starts when a client attaches (no prompt sent), so its slash-command list is ready before the first message; archived chats and sessions with a missing project directory start nothing.
- Slash commands: the agent-reported list (name, description, argument hint, aliases, project/user source; terminal-bound and internal commands hidden) rides in the chat snapshot and as `chat-commands` pushes with loading/ready/unavailable state. The composer's `/` menu opens for the `/` word at the caret anywhere in the message, filters and inserts commands in place without sending; local command output (`/context` etc.) renders in the transcript, and replayed history shows slash-command turns as typed with their output.
- `/clear`, `/reset`, and `/new [name]` never reach the agent: the client creates a new chat in the same project with the same profile and the same approval policy (named when given), selects it, then archives the previous chat; on creation error the current chat is untouched.
- Each chat session has a per-session approval policy (`approval_policy` in `chat_sessions`: `manual`, or `auto`): auto grants tool approvals without cards — AskUserQuestion still asks, and Claude Code settings deny rules still apply. New chats start with the client Settings default (`defaultApprovalPolicy`, `manual` unless saved as `auto`), sent as the optional `approvalPolicy` on `session-create` and overridable per session in the New Session dialog; the server falls back to `manual` when the field is absent. A chat created by `/clear`, `/reset`, or `/new` carries the previous chat's policy over instead of re-reading the default. Toggled live from the chat header's **Auto-approve** switch (`chat-set-approval-policy`); persisted across restart, resume, archive, and restore.
- During an in-flight chat turn, a live activity row ends the transcript (`Waiting for model…` / `Thinking…` / `Writing <tool> input…` / `Running <tool>…` / `Retrying (a/m, status)…` plus a client-ticked elapsed timer). Derived server-side from protocol frames by the pure reducer in `src/server/chat/chatActivity.ts`, delivered on phase changes via the additive `chat-activity` message and `chat-snapshot.activity`; ephemeral (never a sequenced, persisted ChatEvent nor part of the session-list status) and hidden client-side while text streams, a request awaits the user, or the chat is archived.
- Background shells and Monitors a chat agent starts are visible and controllable: a per-session roster (pure reducer `src/server/chat/chatBackgroundTasks.ts`) joins each task to its `Bash`/`Monitor` tool call, rides the additive `chat-background-tasks` message and `chat-snapshot.backgroundTasks` (a full-set level signal, never sequenced events), and persists outcomes in a `chat-tasks/` sidecar (a row still running at restart recovers as stopped; kill deletes the file; archive keeps it). The tool row shows running with a ticking elapsed or the notification's one-line outcome (`✗` on failed), expands to the output tail — at most the last 8 KiB via the SDK's `get_task_output` while the query lives, else the recorded output file in the CLI's `tasks/` layout (`chat-task-output`); plain text with ANSI stripped, truncation noted, unavailable stated — and offers a per-task Stop (`chat-task-stop`), never in archived chats. Running tasks also list in the live strip beside workers. Tasks never change session status: a session whose turn ended reports `waiting` however much runs in the background, and a turn interrupt leaves them running — only process death settles them as stopped.
- Turns the agent starts on its own (a background task completed, a Monitor fired) stream into the transcript like user turns: the driver opens a turn on a `system/init` that arrives with no active turn (`session_state_changed` is `sdk_host_only` and never reaches SDK consumers), and `turn_started` carries a `trigger` — the buffered task notifications, or `resumed` when the cause is unknown. Replay maps task-notification transcript records to the same trigger line instead of a user bubble.
- Mailbox recovery also runs when a recipient finishes a turn, fails, is archived, or is killed: recorded receipts settle; unconfirmed pushed mail is held for review. In-flight claims remain visible as Receiving. Retry refuses a killed recipient, and killed-sender thread context includes only confirmed delivered messages. `/clear`, `/reset`, and `/new` clone an existing chat’s stored group even when its definition is missing; ordinary creation still refuses unknown groups.
- Chat sessions show per-profile plan usage in a bar under the chat header (`UsageBar.tsx`): one thin meter per plan window (5-hour, 7-day, per-model weekly) with percent used and local reset time, plus a tick on the meter's track at the share of the window already elapsed (from the server-supplied `periodMs` — set in `usageWindowPeriods.ts` for known Claude kinds, never for provider quota rows — and `resetsAt`; moved by a minute client clock, hidden once the reset passes; the row's hover text and the track's `aria-label` state used vs. elapsed and time left). `rate_limit_event` pushes and `/usage` reports are normalized by the SDK-free parsers in `src/server/chat/usageLimits.ts`, kept per Claude profile in memory only (never persisted; absent after a restart until the next update), delivered through `chat-snapshot.usage` and the additive `chat-usage` message, and gap-filled once per profile by the SDK's experimental usage pull when nothing has arrived. The SDK pull follows the host CLI login rather than the session's provider, so for a profile whose base URL serves the Z.AI coding-plan quota endpoint (`/api/monitor/usage/quota/limit` — undocumented; strict shape check in `src/server/chat/zaiUsage.ts`) the server instead pulls plan usage with the profile's own credentials in that slot (`source: 'provider'`), suppresses the host-login pull for it, and refreshes it every 10 minutes while a session of the profile has a started agent; profiles routed elsewhere (GLM gateways without the endpoint, MiMo, …) still show the logged-in claude.ai account's plan, and profiles with no usage source (API key, no login, no quota endpoint) show no bar.
- Chat sessions show CLI-style notices in a strip under the chat header (`NotificationStrip.tsx`), beside the usage bar, from two sources: account notices the server computes per profile (`src/server/chat/accountNotices.ts` mirrors the CLI's login-expiry rule from `.credentials.json` — shown while the refresh token expires within 3 days — checked on attach, agent start, and a 30-minute timer) and agent notices mapped from the SDK's `system`/`notification` frames (same-key replacement, `timeout_ms` expiry, cleared when the agent process ends: archive, kill, restart, shutdown, or an unexpected exit — the driver's in-place respawn then starts clean). Notices are ephemeral like activity: held in server memory, carried by `chat-snapshot.notifications` and the additive `chat-notifications` push, never persisted, sequenced, or replayed, and never part of the session-list status. Closing is per source: agent notices dismiss server-side (`chat-dismiss-notification`, every attached client); account notices hide in that browser tab only, keyed by text so a new day count shows them again.
- Agent teams share one git repository, including linked worktrees; plain directories form their own team. Role groups load from the main checkout's `.kawai/groups/<id>.md`, layered over `~/.kawai/groups/`. A chat chooses its fixed group at creation. Its role body and mailbox note are re-read only when its agent starts; a missing group keeps its badge but receives no new group mail.
- Each chat has an in-process `kawai-team` MCP server with `send_message`, `reply`, `schedule_message`, and `list_groups`, allowed without approval cards under either policy. Kawai supplies sender identity, group, and origin path; recipients must belong to the same team, and direct mail restores an archived recipient. Messages persist in SQLite and arrive as peer turns with a message id and thread. Normal mail waits for an idle agent with no pending card or live worker; urgent mail comes first, direct before group, then oldest. Group mail goes to the longest-idle member exactly once. Urgent direct mail interrupts only after pending cards resolve and the SDK confirms interruption; urgent group mail waits for idle. Scheduled mail survives restarts.
- Replies keep their thread: an archived sender is restored; a killed sender's reply falls back to its stored group with the full thread, or is dead-lettered if no group remains. Queued direct mail to killed recipients is dead-lettered. Threads stop at the sender group's `hopLimit` (default 20); a human retry resets the hop count.
- Team tasks (group settings): group frontmatter also takes `canCreateTasks: true|false` (default false: members cannot create tasks), `canCreatePlans: true|false` (default false: members cannot call `plan_create`; a strict boolean, an invalid value rejects the file like `canCreateTasks`; the human sets it, typically on the lead group), `max: <n>` (live members of the group before worktree staffing stops spawning; default 1), `profile: <id>` (profile for spawned members; default profile when unset; profile routing generalizes it to `profiles`), `approval: manual|auto` (spawned members' policy; default manual), `canManageMailbox: true|false` (default false; see the mailbox management bullet; an invalid value is a group warning and stays false), `effort: low|medium|high|xhigh|max` (reasoning effort every member's agent — spawned or human-created — launches with, as the SDK `effort` option/`--effort`; read at each agent start like the role prompt, so edits reach only later starts; unset = Claude Code settings decide; an invalid value is a group warning and is ignored; `CLAUDE_CODE_EFFORT_LEVEL` and a settings maximum still override or clamp it), `releaseOnTaskClose: true|false` (default true: a task's spawned members are released when it closes), `worktreeScoped: true|false` (default true: task mail is scoped to the task's worktree), and `canReleaseMembers: true|false` (default true: members may call `release_member`) — those three are strict booleans, invalid values reject the file like `canCreateTasks`. Spawn caps per team live only in the user-level `~/.kawai/teams.json` — `{ "maxSpawnedSessions": 5, "teams": { "/path/to/repo-or-worktree": { "maxSpawnedSessions": 8 } } }` — default 5, keys resolved to the repository's team, re-read when the file changes; a malformed file or value is logged and the default applies; project files can never set it. A member's worktree is the nearest enclosing directory holding `.git` (so a member in `<worktree>/src` still counts as in `<worktree>`); task targets must be the main checkout or a linked worktree listed by `git worktree list` and are stored as that root. Kawai never creates a worktree to satisfy a message.
- Team tasks are kawai-owned SQLite rows (`team_tasks`, `team_task_revisions`, `team_task_journal`; nullable `task_id` on `team_messages` and `chat_sessions`), scoped to one team: title, status (`open`/`active`/`blocked`/`done`/`cancelled`), creator (the human or an agent session), optional parent task, target worktree, and linked OpenSpec change. Direction and acceptance criteria live in numbered, immutable revisions (each publication adds one; earlier ones stay viewable); the journal is append-only. Tasks never belong to a session: archiving or killing the creator or any participant leaves the task, its revisions, and its journal in place, and participants are derived from the creator, associated sessions, task mail, and journal authors. Task status is kawai's own — it never rewrites an OpenSpec change's `tasks.md` checkboxes; a linked change's artifacts are only referenced as the authoritative direction.
- Mailbox management (`team-mailbox-management`): the `kawai-team` server also carries `list_mailbox`, `cancel_message`, and `discard_message`, allowed without cards and refused by right at each call from the caller's current group file (`src/server/team/mailboxManagement.ts`). Any agent lists the unsettled mail it sent, received, or holds and cancels its own mail while queued, scheduled, or awaiting a request; a `canManageMailbox` group sees and cancels any team message in those states plus `parked` work, and discards `dead`/`uncertain` mail. Claimed, spawning, and delivered mail is never cancellable; retry and hand-off stay human-only. Agent cancel and discard require a reason (cut to 300 characters; the row's `reason` reads `cancelled by <session>: …`), refusals name the state or missing right and write nothing, and another team's ids read as not found. `MailboxStore.cancel(id, actor, reason?)` is the one path for the human panel and agents: the store keeps one invariant, parked work always has a live resume or is cancelled with it: a parked cancel cancels its `queued`/`awaiting-request` resume in the same transaction (so a resume can never deliver after it), is refused with `resume-in-flight` (holder named) while the resume is claimed or delivered, and a resume linked to parked work refuses every cancel (`linked-resume`, parked id named) — kawai's own re-park, unpark, release, and forward go through `replaceResume`; a cancelled holder is un-paused but neither restored nor resumed, and `LimitOutcomes` defensively drops work that is no longer parked or delivered. The event log's actor vocabulary is `system`/`human`/`agent`, the last with a nullable `actor_session` column (additive; old rows null), kept separate from the task journal's author and from `TeamActor`; a task-bound cancel appends a journal note authored by the acting agent. The Mailbox tab offers Cancel on parked rows beside Hand off and shows each row's short id (first 8 characters, full id copyable).
- Task rights and tools: the human creates, drafts and publishes direction, notes, and sets any status (including reopening) from the UI; an agent creates only when its group's current file sets `canCreateTasks: true`, becoming the creator. Only the creator or the human amends direction/acceptance (refusals point to a note or a message to the creator); any team member appends journal notes and sets `active`/`blocked`; only the creator sets `done`/`cancelled`. The `kawai-team` server adds `task_create` (title, direction, optional acceptance, parent_id, worktree, openspec_change), `task_get` (full record: revisions, journal, subtasks, messages), `task_note`, `task_update_status` (status, optional journaled note), `task_amend` (direction and/or acceptance, optional `rationale` and `notify`; publishes the next revision at once — agents have no drafts), `task_list` (optional status), `task_acknowledge` (task id and revision), and the result tools `task_submit_result`, `task_submit_findings`, and `task_handoff` (see the results bullet), all allowed without cards; identity is bound to the calling session. References are checked first: parents must be tasks of the same team, worktrees must be listed worktree roots, and linked changes must exist under `openspec/changes/` in the main checkout or the task's worktree. The system prompt's task note explains these rules and that a linked change's proposal, design, and tasks are authoritative.
- Task mail: `send_message`, `reply`, and `schedule_message` take an optional `task_id` of the sender's team (unknown or other-team ids are refused and nothing is queued); a reply without one keeps its original message's task. The task context is built when the message is delivered, not when it is sent, so it reflects amendments and notes made while it waited: the envelope metadata gains `task` (`id`, `title`, `status`, `revision`, `direction`, `acceptance`, `openspecChange`, `worktree`, and `journal` — the last 5 entries, each cut at 500 characters; `task_get` has the rest), and a readable header precedes the body, stating that a linked OpenSpec change's proposal, design, and tasks are the authoritative direction. Envelopes without a task keep the old shape. Receiving task mail associates the session with that task (`chat_sessions.task_id`), which its chat header shows; a spawned member keeps the task it was spawned for.
- Waiting reasons (team-waiting-reasons): the Mailbox tab shows every unsettled state with exactly one section, in a fixed order — Held for review, Dead letters, Parked, Starting agent, Queued, Receiving, Scheduled — the first three expanded by default and the rest collapsed behind their counts; a search narrows every section over participants, bodies, and reason text, empty sections can be hidden, and routing state is its own collapsible section. Each unsettled row carries a server-computed reason: an immediate blocker plus the other constraints that also apply, ordered deterministically with capacity first (group cap, per-profile cap, team spawn cap, worktree occupancy), then member facts, then spawn/routing specifics; a `spawning` row's blocker is always Starting agent, its own reservation's capacity effects listed among the others. Reasons are derived from the same dispatch, staffing, and routing state that makes the delivery decision (a cause reporter beneath the unchanged eligibility/claim predicates; the router's `none`/`hold` carry a diagnosis; direct mail reads the recipient view), held in memory only (rebuilt by the first pass after a restart, never persisted), refreshed on every dispatch pass, and re-published when a team's reasons structurally change — including reason-only changes with no row state change. `team-mailbox-snapshot` carries them beside the worktree occupancy roster (`worktrees`: live sessions per resolved worktree root plus pending reservations — manual sessions listed, only spawned ones and reservations counting as writers). Dead letters show readable labels for known codes (`worktree-missing`, `killed-recipient`, `killed-sender-without-group`, `hop-limit`) with the raw code still visible; unknown codes render verbatim. Named sessions in reasons link to their chats; worktrees show their basename with the full path available.
- Worktree staffing: group mail whose task targets a worktree goes only to an idle member of that group whose resolved worktree is the target (other ordering rules unchanged); members elsewhere skip it — unless the receiving group's current file sets `worktreeScoped: false` (member-release), in which case any idle member of the group takes it wherever it runs and the mail never spawns; a missing group definition counts as scoped. After each dispatch pass, such mail that no idle matching member took triggers a spawn: a new chat of that group in the worktree root, with the group's `profile` and `approval`, associated with the task and marked spawned (`chat_sessions.spawned`); the message becomes its first turn, delivered once. Spawning waits (and is re-evaluated whenever a member idles, archives, or is killed) while the group has `max` live members (every non-archived member counts, spawned or created by the human), the team has its `maxSpawnedSessions` live spawned sessions (only spawned ones count), or the worktree already has a live spawned member of any group (counted by resolved worktree, so one in a subdirectory still holds it). The cap check and the reservation (message state `spawning`, durable `team_spawns` row) are one transaction, with the reservation row inserted before the flip so the reserve notify's snapshot already sees it; a reserve that fails throws inside that transaction (rolling the insert back) and reaches the dispatcher's error path. A failed spawn drops the reservation, requeues the mail, and retries when its 30 s backoff ends — the dispatcher's timer is woken at that moment, so the retry needs no unrelated change. Startup drops leftover reservations and requeues their mail (never pushed, so receipt recovery is not involved). Queued task mail whose worktree no longer exists is dead-lettered `worktree-missing: <path>`; kawai never creates a worktree.
- Member release (team-member-release): when a task becomes `done` or `cancelled`, its live spawned members (never human-created sessions, and never members of a group whose current file sets `releaseOnTaskClose: false`) are marked pending release in the same close transaction — which also dead-letters the task's undelivered group mail to worktree-scoped groups as `task-closed` (direct mail and unscoped groups are untouched, at the close and for late arrivals in the dispatcher), so a done task never delivers its instruction late or spawns a fresh dev. A pending member is released — archived through the same path as a human archive, never killed — as soon as it is ready: idle, no pending approval or question, no live background worker, no running background task, no claimed or parked mail, no due direct mail (the one readiness definition, shared with the `release_member` tool and future hand-off flows; unavailable members count as ready). Evaluation runs in the dispatcher's `beginCycle` — awaited before the pass's diagnoses are collected, so a dead-lettered row is never reported as waiting and freed capacity serves waiting mail in the same pass. Pending releases are durable rows (`team_member_releases`), survive restart, and are cancelled by reopening the task or by any archive, kill, or human restore of the member (a restored member is never released again for the same close). A spawn still in flight at close gets its reserved message dead-lettered; the new session starts with no first turn, is marked at creation, and is released once idle. Every release appends a task-journal entry authored by kawai (`system`, rendered "Kawai", kept separate from `TaskActor` so the system is never a sender or creator) naming the session and why.
- `release_member` (member-release): a `kawai-team` tool, allowed without cards, that members of a group not setting `canReleaseMembers: false` (default permitted) can use to release one spawned member of their team immediately — archive only; no kill or restore tool exists. Refused with a specific reason — never deferred — for the caller itself, human-created sessions, other teams, archived or unknown sessions, and members that are busy, awaiting a request, running a background worker or background task, or holding mail. Success journals the release on the target's task; a settled member of an open task can be released to free its writer slot, leaving the task, its status, and its delivered mail untouched.
- Task assignment (`team_task_assignments`, plus nullable `team_tasks.request_key`) names who is responsible for a task, separately from the derived participant list: one append-only row per dispatch — target (a group, its role, or a session), the initial instruction verbatim, the dispatcher, the request key, the claim, and supersession. The state is never stored: it derives at read time from the instruction mail (queued while queued/spawning/awaiting-request, claimed, delivered, failed when the mail settles dead/cancelled/discarded with the reason shown, parked/forwarded/uncertain keeping their names, superseded from the row), and the claim is copied from the mail and cleared again on release or requeue. The outstanding assignment is the newest row that is neither superseded nor failed (delivered work stays outstanding until superseded; a failed instruction frees the task for reassignment) and rides `TeamTaskSummary`; the whole history rides the detail. Assigning changes no task status.
- Human dispatch: **Create and assign** and **Assign / send task** run through `AssignmentService` as the human for the session's team, committing the assignment row and its instruction mail in one SQLite transaction (a refusal writes nothing; an accepted dispatch always has its mail). The instruction is an ordinary `team_messages` row whose sender is the human on the actor model `team-message-threads` ships (`from_kind: 'human'`, no sender session, origin = the team's main checkout root) — so claims, receipts, routing, worktree filtering, and spawning all apply unchanged, and an agent's reply in the dispatched thread reaches the human exactly as that change specifies (settled on send, toast, thread row; the task journal stays a complementary record). Create and dispatch carry a stable client request key, unique per team on both tables: a reconnect resend, a double click, or a replay of the same key and payload returns the prior outcome and never duplicates a task or an instruction; the same key with a different payload is refused naming the differing field, and the armed create key is re-minted when the form changed after a lost result. When creation commits but dispatch is refused, the task stays, every form field remains, and **Retry assignment** reuses the existing task and key (an edited target or instruction re-keys: the refused dispatch wrote nothing).
- Reassignment is an explicit handoff: dispatching onto an outstanding assignment requires the human to choose **notify** or **stop**. **Stop** supersedes it and cancels the old instruction only while queued or awaiting-request (a `spawning` reservation is left to staffing's lifecycle; claimed or delivered work is never auto-cancelled; nobody is killed or archived). **Notify** supersedes it and sends the previous claimed agent — when one exists — a fixed normal-priority direct note ("Task … was reassigned to …; your work is not cancelled — report status with a journal note if still relevant."), degrading to a plain supersede without a claim. All reassignment writes commit with the dispatch. A read-only preview (`team-task-preview`) answers the target worktree, role, effective profile (the session's, or the first profile a spawn could use), approval policy, staffing availability, and — warned, never blocked — a session target outside the task's worktree; dispatch revalidates everything. Dispatch never creates a worktree: the worktree pickers link into the existing creation flow and refresh on return.
- Task revision publication (task-revision-publication): the human edits a task's direction as a **draft** (`team_task_drafts`: one per task, direction, acceptance, rationale, and the published revision it is based on) that publishes nothing — no revision, no `updated_at`, no mail, no task-change event (its own listener refreshes only the human's view), never in `task_get` or a delivered header (`HumanTaskDetail` is the only detail type with a `draft`). **Publish revision N** / **Publish and notify** record the next immutable revision with its rationale, author, command key, and notify flag (nullable columns on `team_task_revisions`, old rows read as "published before notifications"): one transaction resolves the key first (a same-payload replay returns the prior revision; a different payload is refused naming the field), then refuses a stale base naming the newer revision (the draft stays; **Rebase onto revision M** moves only its base), inserts N+1, and drops the draft when the publication came from it (`fromDraft`, set whenever a draft exists — edits beyond the saved text still replace the one draft) — the partial unique `(task_id, request_key)` is the arbiter, and a request that loses a same-key race resolves as the replay. `TaskStore.changed` fires once per new revision, never for a replay, refusal, or draft. Notices (`taskNotices.ts`, `team_task_notifications`) are written in that same transaction: one direct, normal-priority task message tagged `task-revision` with `revision_notice` (`revisionNotice` in the envelope) to the outstanding assignment's current claimant (following forwarded work to its successor), never group mail — an unclaimed group assignment needs none, its instruction is built with the newest revision at push; a killed claimant's notice is dead-lettered while the revision stands, an archived one is restored after commit. **Notify** / **Retry notification** (`team-task-notify`) is one keyed command that sends each holder lacking the revision (not delivered it or newer, no pending or uncertain notice) one notice and never writes a revision; its replay sends nothing. The publication detail derives per holder, never stored and never merged: notice state (Not notified, Queued, Delivered, Failed with reason, Uncertain — linked to the Mailbox, whose Retry/Discard resolves it), the delivered revision (highest `task_revision` of task mail delivered to it), and the acknowledged revision. Agents call `task_acknowledge` (`team_task_acknowledgements`, keyed by session; unpublished revisions and other teams refused, repeats no-ops) once they work from a revision; only the current claimant's acknowledgement shows, so a reassigned, requeued, or forwarded holder starts unacknowledged, earlier rows staying in the history. Delivered rows keep the revision they carried. The revision-published contract is the `team_task_revisions` row plus `team_tasks.revision`, compared at read time; `TaskService.onRevisionPublished` is an optional after-commit announcement (never on a replay, draft, notice, retry, or acknowledgement) that nothing depends on. The UI's publish and notify keys live in the task store per armed slot — reused while the payload is unchanged (double click, reconnect resend; Notify and Retry notification are distinct payloads, so a Retry after a lost Notify result is a new command), retired on success.
- Task results and handoffs (task-results-handoffs): a result is a `team_task_results` row — summary, commit and/or diff, the worktree (the task's, else the submitter's), test outcomes shown labeled **(claimed)** and never verified, limitations, the submitter, and the task revision pinned at submission; a newer result supersedes the outstanding one (both stay readable). **Needs re-evaluation** is derived at read time (pinned revision older than the task's current one), never stored. Agents submit with `task_submit_result` (a new result per call) and review/QA findings with `task_submit_findings` (`team_task_findings`), bound to the exact result examined — never transferred to a later one — and recording the handoff they answer when the caller holds it. Handoffs (**Request review**, **Request QA**, **Return for fixes**; agent `task_handoff`) are ordinary task-assignment dispatches whose row also carries `handoff_kind`, `result_id`, and `expected_response` — all part of the request key's payload identity — with an instruction naming the result and commit; every handoff supersedes the outstanding assignment as the next stage through reassignment's **stop** branch — no notify/stop choice, no reassignment note, a journal line naming the handoff kind, and the predecessor's instruction cancelled only while queued or awaiting a request (claimed or delivered work is never touched), so a superseded stage never delivers later — and the request-key replay and an agent's retry, which returns the standing equivalent handoff instead of dispatching twice, both resolve before supersession, so neither supersedes its own handoff. Acceptance (**Accept result** / `team-task-accept-result`) checks closing rights first with the exact `done` rule (the human, or the creator agent) — a contributor's accept writes nothing — shows the acceptance criteria and open child tasks, and requires a stated reason when the result needs re-evaluation or children are open; the acceptance, its journal entry, and `done` commit in one transaction. Acceptance is per task: a finished child never closes its parent. **Release worktree and hand off** (human only, `team-task-release`) archives the task's live spawned members through member release's readiness, archive, and journal paths, then dispatches the review; any member not ready (awaiting an approval or answer, busy, running a worker, holding mail) refuses the whole action with its name and reason, archiving and dispatching nothing. The confirmation lists who is archived and, separately, other live sessions in the worktree that stay and can still edit it. A review handoff of the outstanding result already queued behind the occupied worktree is the one that proceeds — release never dispatches a second.

- Product strategy is a kawai-owned SQLite record (`product_strategies`, `strategy_revisions`, `strategy_drafts`, `strategy_evidence`, `strategy_decisions`, `strategy_impact_reviews`, `strategy_repo_bindings`, beside the team tables): one record per product with a human owner, repository bindings (the owning team's git common dir plus its listed worktrees — the unique root binding enforces one product per team), and a current approved revision. Every revision's content is the structured template (purpose, primary users, needs/outcomes, main use cases, product approach, principles and trade-offs, boundaries/non-goals, success measures, assumptions and evidence, open questions, decisions and revision history) normalized to all sections — prose may be explicitly empty — and hashed over a canonical serialization (stable key order), so approval and CAS compare hashes.

- Strategy approval is human-only and a runtime record: `strategy_decisions` is written only through the human UI action path (`strategy-approve`/`strategy-withdraw` over the chat WebSocket, actor `{ kind: 'human' }`), and `StrategyService` refuses an agent caller on those paths. Idempotency is a database fact — `UNIQUE(strategy_id, command_id)` on both decisions and impact reviews — so a retry with the same command id and payload returns the prior result, the same id with a different payload is refused, and a stale state (withdrawn/superseded revision, drifted hash, or a changed active revision under its prior value) is refused as stale; two racing approvals never leave two actives. - Plans (durable-plans) are kawai-owned SQLite records of one team (`plans`, `plan_revisions`, `plan_drafts`, `plan_events` in `src/server/plans/`, beside the task and strategy tables): a title, a creator, a stored lifecycle (`open`/`completed`/`cancelled`), and a current approved revision; the human is every plan's owner and only approver, and archiving or killing the creating session leaves the plan. - Plan approval and lifecycle (durable-plans, `plan-approval`): only the human approves, withdraws, discards, completes, cancels, or reopens a plan — `PlanService` refuses an agent caller first, no agent tool exists for any of them, and a file, message, or draft claiming approval grants nothing. - Unsubmitted composer input is a per-session client-side draft (keyed by session id in `chatStore.drafts`): it survives switching chats and reconnects and returns after archive → restore, clears on submit, and is discarded on kill; it is never sent to the server or restored after a page reload.
- Database safety (execution-safety-recovery D13–D15, `src/server/dbSafety/`): `schema_migrations` records each applied version (number, name, time, build, pre-migration backup path) and `PRAGMA user_version` mirrors the highest, never read for a decision. `initDatabase` reads the version without writing; a database newer than the build is refused before any write (`DatabaseStartupError`: both versions, the newest `pre-migration-<n>` backup, `docs/operations/database-backups.md`; the server exits, no override). Then it takes the `startup` snapshot; only on a database with no recorded version it runs the frozen baseline (`baseline.ts`: `applySessionSchema` plus every store's schema function — stores never create their own tables, so store-level tests use `schemaDb()`) and records version 1 `baseline` (one transaction on a database with no tables, each step committing alone on a pre-version database); then each pending entry of `MIGRATIONS` (empty today; versions dense from 2) runs only after its `pre-migration-<n>` backup is renamed into place and passes its check, its `up(db)` and version row in one `BEGIN IMMEDIATE` transaction — a failed backup or migration rolls back and refuses start naming both. Every later schema change is a new numbered migration, never a baseline edit. `DatabaseBackups` (`backups.ts`) copies with `serialize()` on the server's own connection outside any transaction (retried up to 3 times), writes `<name>.partial`, fsyncs, renames to `backups/<stem>-<UTC stamp>-<reason>.db`, and runs `integrity_check` over a separate read-only connection, renaming a failing copy `.corrupt` (logged, kept in `status()` failures, out of rotation); the hourly `interval` snapshot is skipped while `total_changes()` equals the last snapshot's stored value. Rotation (`backupFiles.ts`, at startup and after each snapshot) keeps 24 `interval`, 7 `startup`, every backup of the newest 3 migrations, and the newest 3 `.corrupt` and 3 `.partial` (never the one being written); other files in `backups/` are never touched. In-memory databases take no backups. Backups stay on the host; the restore procedure and what it does not bring back are in `docs/operations/database-backups.md`.
- Navigator: live sessions sit in OpenSpec change/worktree sections; hibernating, history, and archived sessions collect in the docked `Archive` pane (newest first, collapsed until first expanded). `Remote` holds only live sessions on other hosts.

## Git

- Check `git status`/`git diff` before commits
- Atomic commits; push only when asked
- Never destructive ops (`reset --hard`, `force push`) without explicit consent
- Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`
- Commit early and often — make small, incremental commits as you work rather than one large commit at the end.

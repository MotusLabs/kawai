# AGENTS.md

- Bun 1.x, TypeScript 5.x, React 18, Hono, xterm.js, Zustand, Tailwind.

## Commands

```
bun run dev        # frontend + backend
bun run build      # production build
bun run lint       # oxlint
bun run typecheck  # tsc --noEmit
bun run test       # unit tests
```

Run `bun run lint && bun run typecheck && bun run test` after changes.

## How It Works

- Single tmux session (default: `agentboard`) with one window per project
- Backend discovers windows, streams terminal output via WebSocket
- Parses Claude/Codex JSONL logs from `~/.claude/projects/` and `~/.codex/sessions/` for status
- Status: unknown -> working -> waiting (derived from log events)
- Chat sessions use the Claude Agent SDK without tmux, driving a separately installed Claude Code executable (`KAWAI_CLAUDE_PATH` or `claude` on the server PATH; version-checked against the SDK-pinned baseline 2.1.289 before creation — the SDK's platform CLI packages are stubbed out of the install, so Claude Code must be installed on the host). Turns and pending approvals/questions determine status directly. WebSocket snapshots restore history and pending requests on reconnect; SQLite rows and SDK transcripts allow restart/resume.
- The chat agent starts when a client attaches (no prompt sent), so its slash-command list is ready before the first message; archived chats and sessions with a missing project directory start nothing.
- Slash commands: the agent-reported list (name, description, argument hint, aliases, project/user source; terminal-bound and internal commands hidden) rides in the chat snapshot and as `chat-commands` pushes with loading/ready/unavailable state. The composer's `/` menu opens for the `/` word at the caret anywhere in the message, filters and inserts commands in place without sending; local command output (`/context` etc.) renders in the transcript, and replayed history shows slash-command turns as typed with their output.
- `/clear`, `/reset`, and `/new [name]` never reach the agent: the client creates a new chat in the same project with the same profile and the same approval policy (named when given), selects it, then archives the previous chat; on creation error the current chat is untouched.
- Each chat session has a per-session approval policy (`approval_policy` in `chat_sessions`: `manual`, or `auto`): auto grants tool approvals without cards — AskUserQuestion still asks, and Claude Code settings deny rules still apply. New chats start with the client Settings default (`defaultApprovalPolicy`, `manual` unless saved as `auto`), sent as the optional `approvalPolicy` on `session-create` and overridable per session in the New Session dialog; the server falls back to `manual` when the field is absent. A chat created by `/clear`, `/reset`, or `/new` carries the previous chat's policy over instead of re-reading the default. Toggled live from the chat header's **Auto-approve** switch (`chat-set-approval-policy`); persisted across restart, resume, archive, and restore.
- During an in-flight chat turn, a live activity row ends the transcript (`Waiting for model…` / `Thinking…` / `Writing <tool> input…` / `Running <tool>…` / `Retrying (a/m, status)…` plus a client-ticked elapsed timer). Derived server-side from protocol frames by the pure reducer in `src/server/chat/chatActivity.ts`, delivered on phase changes via the additive `chat-activity` message and `chat-snapshot.activity`; ephemeral (never a sequenced, persisted ChatEvent nor part of the session-list status) and hidden client-side while text streams, a request awaits the user, or the chat is archived.
- Mailbox recovery also runs when a recipient finishes a turn, fails, is archived, or is killed: recorded receipts settle; unconfirmed pushed mail is held for review. In-flight claims remain visible as Receiving. Retry refuses a killed recipient, and killed-sender thread context includes only confirmed delivered messages. `/clear`, `/reset`, and `/new` clone an existing chat’s stored group even when its definition is missing; ordinary creation still refuses unknown groups.
- Chat sessions show per-profile plan usage in a bar under the chat header (`UsageBar.tsx`): one thin meter per plan window (5-hour, 7-day, per-model weekly) with percent used and local reset time. `rate_limit_event` pushes and `/usage` reports are normalized by the SDK-free parsers in `src/server/chat/usageLimits.ts`, kept per Claude profile in memory only (never persisted; absent after a restart until the next update), delivered through `chat-snapshot.usage` and the additive `chat-usage` message, and gap-filled once per profile by the SDK's experimental usage pull when nothing has arrived. The SDK pull follows the host CLI login rather than the session's provider, so for a profile whose base URL serves the Z.AI coding-plan quota endpoint (`/api/monitor/usage/quota/limit` — undocumented; strict shape check in `src/server/chat/zaiUsage.ts`) the server instead pulls plan usage with the profile's own credentials in that slot (`source: 'provider'`), suppresses the host-login pull for it, and refreshes it every 10 minutes while a session of the profile has a started agent; profiles routed elsewhere (GLM gateways without the endpoint, MiMo, …) still show the logged-in claude.ai account's plan, and profiles with no usage source (API key, no login, no quota endpoint) show no bar.
- Chat sessions show CLI-style notices in a strip under the chat header (`NotificationStrip.tsx`), beside the usage bar, from two sources: account notices the server computes per profile (`src/server/chat/accountNotices.ts` mirrors the CLI's login-expiry rule from `.credentials.json` — shown while the refresh token expires within 3 days — checked on attach, agent start, and a 30-minute timer) and agent notices mapped from the SDK's `system`/`notification` frames (same-key replacement, `timeout_ms` expiry, cleared when the agent process ends: archive, kill, restart, shutdown, or an unexpected exit — the driver's in-place respawn then starts clean). Notices are ephemeral like activity: held in server memory, carried by `chat-snapshot.notifications` and the additive `chat-notifications` push, never persisted, sequenced, or replayed, and never part of the session-list status. Closing is per source: agent notices dismiss server-side (`chat-dismiss-notification`, every attached client); account notices hide in that browser tab only, keyed by text so a new day count shows them again.
- Agent teams share one git repository, including linked worktrees; plain directories form their own team. Role groups load from the main checkout's `.kawai/groups/<id>.md`, layered over `~/.kawai/groups/`. A chat chooses its fixed group at creation. Its role body and mailbox note are re-read only when its agent starts; a missing group keeps its badge but receives no new group mail.
- Each chat has an in-process `kawai-team` MCP server with `send_message`, `reply`, `schedule_message`, and `list_groups`, allowed without approval cards under either policy. Kawai supplies sender identity, group, and origin path; recipients must belong to the same team, and direct mail restores an archived recipient. Messages persist in SQLite and arrive as peer turns with a message id and thread. Normal mail waits for an idle agent with no pending card or live worker; urgent mail comes first, direct before group, then oldest. Group mail goes to the longest-idle member exactly once. Urgent direct mail interrupts only after pending cards resolve and the SDK confirms interruption; urgent group mail waits for idle. Scheduled mail survives restarts.
- Replies keep their thread: an archived sender is restored; a killed sender's reply falls back to its stored group with the full thread, or is dead-lettered if no group remains. Queued direct mail to killed recipients is dead-lettered. Threads stop at the sender group's `hopLimit` (default 20); a human retry resets the hop count.
- Team tasks (group settings): group frontmatter also takes `canCreateTasks: true|false` (default false: members cannot create tasks), `max: <n>` (live members of the group before worktree staffing stops spawning; default 1), `profile: <id>` (profile for spawned members; default profile when unset; profile routing generalizes it to `profiles`), and `approval: manual|auto` (spawned members' policy; default manual). Spawn caps per team live only in the user-level `~/.kawai/teams.json` — `{ "maxSpawnedSessions": 5, "teams": { "/path/to/repo-or-worktree": { "maxSpawnedSessions": 8 } } }` — default 5, keys resolved to the repository's team, re-read when the file changes; a malformed file or value is logged and the default applies; project files can never set it. A member's worktree is the nearest enclosing directory holding `.git` (so a member in `<worktree>/src` still counts as in `<worktree>`); task targets must be the main checkout or a linked worktree listed by `git worktree list` and are stored as that root. Kawai never creates a worktree to satisfy a message.
- Team tasks are kawai-owned SQLite rows (`team_tasks`, `team_task_revisions`, `team_task_journal`; nullable `task_id` on `team_messages` and `chat_sessions`), scoped to one team: title, status (`open`/`active`/`blocked`/`done`/`cancelled`), creator (the human or an agent session), optional parent task, target worktree, and linked OpenSpec change. Direction and acceptance criteria live in numbered, immutable revisions (an amendment adds one; earlier ones stay viewable); the journal is append-only. Tasks never belong to a session: archiving or killing the creator or any participant leaves the task, its revisions, and its journal in place, and participants are derived from the creator, associated sessions, task mail, and journal authors. Task status is kawai's own — it never rewrites an OpenSpec change's `tasks.md` checkboxes; a linked change's artifacts are only referenced as the authoritative direction.
- Task rights and tools: the human creates, amends, notes, and sets any status (including reopening) from the UI; an agent creates only when its group's current file sets `canCreateTasks: true`, becoming the creator. Only the creator or the human amends direction/acceptance (refusals point to a note or a message to the creator); any team member appends journal notes and sets `active`/`blocked`; only the creator sets `done`/`cancelled`. The `kawai-team` server adds `task_create` (title, direction, optional acceptance, parent_id, worktree, openspec_change), `task_get` (full record: revisions, journal, subtasks, messages), `task_note`, `task_update_status` (status, optional journaled note), `task_amend` (direction and/or acceptance), and `task_list` (optional status), all allowed without cards; identity is bound to the calling session. References are checked first: parents must be tasks of the same team, worktrees must be listed worktree roots, and linked changes must exist under `openspec/changes/` in the main checkout or the task's worktree. The system prompt's task note explains these rules and that a linked change's proposal, design, and tasks are authoritative.
- Task mail: `send_message`, `reply`, and `schedule_message` take an optional `task_id` of the sender's team (unknown or other-team ids are refused and nothing is queued); a reply without one keeps its original message's task. The task context is built when the message is delivered, not when it is sent, so it reflects amendments and notes made while it waited: the envelope metadata gains `task` (`id`, `title`, `status`, `revision`, `direction`, `acceptance`, `openspecChange`, `worktree`, and `journal` — the last 5 entries, each cut at 500 characters; `task_get` has the rest), and a readable header precedes the body, stating that a linked OpenSpec change's proposal, design, and tasks are the authoritative direction. Envelopes without a task keep the old shape. Receiving task mail associates the session with that task (`chat_sessions.task_id`), which its chat header shows; a spawned member keeps the task it was spawned for.
- Worktree staffing: group mail whose task targets a worktree goes only to an idle member of that group whose resolved worktree is the target (other ordering rules unchanged); members elsewhere skip it. After each dispatch pass, such mail that no idle matching member took triggers a spawn: a new chat of that group in the worktree root, with the group's `profile` and `approval`, associated with the task and marked spawned (`chat_sessions.spawned`); the message becomes its first turn, delivered once. Spawning waits (and is re-evaluated whenever a member idles, archives, or is killed) while the group has `max` live members (every non-archived member counts, spawned or created by the human), the team has its `maxSpawnedSessions` live spawned sessions (only spawned ones count), or the worktree already has a live spawned member of any group (counted by resolved worktree, so one in a subdirectory still holds it). The cap check and the reservation (message state `spawning`, durable `team_spawns` row) are one transaction. A failed spawn drops the reservation, requeues the mail, and retries no sooner than 30s later; startup drops leftover reservations and requeues their mail (never pushed, so receipt recovery is not involved). Queued task mail whose worktree no longer exists is dead-lettered `worktree-missing: <path>`; kawai never creates a worktree.
- Human task controls go over the chat WebSocket, scoped by a chat session's team (`team-tasks-open`/`close` for the list, `team-task-open`/`close` for a detail; authoritative `team-tasks-snapshot`/`team-task-detail` pushes on every task or task-mail change; another team's task is refused). The human creates tasks (with optional parent, worktree, and linked change), and — regardless of who created a task, including a killed agent — amends its direction, appends notes, and sets any status including reopening (`team-task-create`/`amend`/`note`/`status`, answered by `team-task-result`). Sessions carry `taskId`/`taskTitle` and `spawned`; a spawned session in `permission` status (a pending approval or question) needs attention: its navigator row is flagged and a toast fires on the transition, beside the usual permission sound, whether or not a task view is open. Auto-spawned members use their group's `approval` policy (manual unless the group sets `approval: auto`).
- Task UI: **Tasks** in the chat header's panel switcher opens the team's task panel in the side slot shared with **Debug**, **Mailbox**, **Messages**, and **Strategy** (one at a time). The list shows each task's title, status, creator (`Human`, a session name, or `<id> (gone)` once killed), and participants; **New task** takes a title, direction, optional acceptance criteria, parent task, target worktree, and linked OpenSpec change, and opens the created task. A task's detail shows its current direction and acceptance, **Revision history**, the **Journal** with **Add note**, **Subtasks**, and **Messages**, plus **Save as revision N**, **Mark <status>**, and **Reopen** for closed tasks; every control disables while disconnected and refusals show inline. A chat working on a task names it in the header (`Task …` or `Spawned for task …`; click to open it). Peer-message rows show a collapsible task summary (title, status, revision, worktree, linked change, direction, acceptance, latest journal). In the navigator, chat rows carry `spawned`, task-title, and `needs attention` badges (the last for a spawned session awaiting an approval or answer), under the worktree their current path belongs to.
- Messages view: **Messages** in the chat header's panel switcher opens the team's mail feed in that same one-at-a-time side slot. It is read plus compose — the Mailbox panel keeps every delivery operation (Cancel, Retry, Discard, Hand off, Reload routing rules). One filterable, paged list holds delivered and pending mail newest first (keyset paging over `created_at` and rowid), narrowing by delivery state, priority, and human involvement; a host's own base filters (a task) survive alongside, and **Load more** follows the cursor. Rows name participants — a live session's name, the durable `team_session_directory` for a killed one (`Name (gone)`), `Human` for the human — with the raw id as expandable metadata and only a live or archived participant clickable. Opening a message shows its thread oldest first: each row's reply relation, current recipient, the task revision it carried at delivery, and its append-only `team_message_events` history. The human composer under both writes new mail addressed to one of the team's groups or sessions with an optional task, or a reply addressed to the parent's sender and inheriting that task without restating it. Urgent is explained where it is chosen: normal mail waits its turn; urgent mail interrupts a recipient agent's current turn once any pending approval resolves, or goes to the first idle member of a group. Refusals render inline and every control disables while disconnected. Neither an agent nor the human may start new mail to the human — only a reply in a human-started thread reaches them, settled on send with a toast. An uncertain hold keeps its history in the thread: Retry targets the same recipient with a possible-duplicate notice (the row marks it), or the human discards it. Task detail's Messages section draws the same rows with named participants and a link into each thread. On the wire: one authoritative snapshot per open and reconnect (never on change), unfiltered change pushes the client filters itself, and a thread reply is replace-semantics, re-sent whole when its thread moves.
- Product strategy is a kawai-owned SQLite record (`product_strategies`, `strategy_revisions`, `strategy_drafts`, `strategy_evidence`, `strategy_decisions`, `strategy_impact_reviews`, `strategy_repo_bindings`, beside the team tables): one record per product with a human owner, repository bindings (the owning team's git common dir plus its listed worktrees — the unique root binding enforces one product per team), and a current approved revision. Revisions are numbered and immutable: draft content lives in `strategy_drafts` (keyed by draft id — an agent's session id, or `human`; several drafts per product compete, the human picks on approve), `strategy_submit_for_review` promotes a draft to the next numbered revision with status InReview, approval makes it the active Approved revision and supersedes the prior, and withdrawal marks a revision Withdrawn or discards a draft — superseded and withdrawn revisions stay readable, and a draft never replaces the active approved revision. Every revision's content is the structured template (purpose, primary users, needs/outcomes, main use cases, product approach, principles and trade-offs, boundaries/non-goals, success measures, assumptions and evidence, open questions, decisions and revision history) normalized to all sections — prose may be explicitly empty — and hashed over a canonical serialization (stable key order), so approval and CAS compare hashes.
- Strategy claims carry an evidence kind — owner preference, explicit user statement, agent interpretation, proposed choice, hypothesis, validated observation — plus source, observation context or date, and limitations; a validated observation without a source is refused at save. Success measures record outcome, measure, baseline, and target; values that are not known or agreed are the `Unknown` sentinel, and neither the store nor any tool invents a baseline, target, or metric. Submitted revisions write one evidence row per claim.
- Agent strategy tools (`kawai-team` MCP server): exactly `strategy_list`, `strategy_get`, `strategy_save_draft`, `strategy_submit_for_review` — read and propose, identity-bound to the calling session like the task tools, with draft saves CAS-guarded (`expected_draft_hash`/`expected_base_revision`; a mismatch refuses the write and returns the stored draft so the caller keeps its text). There is no agent tool that approves, publishes, withdraws, or deletes a revision, and none may be added: the boundary is structural (see the approval bullet), and the system prompt's strategy note states the rights without ever claiming agents can approve. An agent saving with no strategy record is told the human captures one; work proceeds without a strategy and none is auto-created.
- Strategy approval is human-only and a runtime record: `strategy_decisions` is written only through the human UI action path (`strategy-approve`/`strategy-withdraw` over the chat WebSocket, actor `{ kind: 'human' }`), and `StrategyService` refuses an agent caller on those paths. An approval binds the exact revision number and content hash, records approval scope and allowed open questions, and updates `current_approved_revision` in one transaction that also supersedes the prior approved revision and creates exactly one `strategy_impact_reviews` row (state `pending`) — nothing else: no Plan, task, mail, tool grant, or interruption. Idempotency is a database fact — `UNIQUE(strategy_id, command_id)` on both decisions and impact reviews — so a retry with the same command id and payload returns the prior result, the same id with a different payload is refused, and a stale state (withdrawn/superseded revision, drifted hash, or a changed active revision under its prior value) is refused as stale; two racing approvals never leave two actives. A repository file, peer message, or draft content asserting a revision is approved grants nothing — only a runtime decision record does. Withdrawal keeps history, decisions, and impact items. The boundary is the same one `team-task-*` human actions have: the guarantee is that no agent tool surface can approve, not that a local process speaking the UI connection protocol can be told from a browser.
- Strategy UI: **Strategy** in the chat header's panel switcher opens `ProductStrategyPanel` in the side slot shared with **Tasks**, **Debug**, **Mailbox**, and **Messages** (one at a time), scoped by the session's team. A product with no record shows the capture affordance (`strategy-capture`: product id, title, initial purpose — creating the record through the first save; offered, never a forced wizard, and work proceeds without it). With a record, direction leads — purpose, primary users, needs and outcomes, main use cases, principles and trade-offs, boundaries, from the approved revision or, until one is approved, the newest InReview revision labeled as not approved — with the record identity, status, approved revision number, hash, and author in supporting detail. Each InReview revision shows a review (`Known` / `Assumed` / `Not decided` findings, the diff summary from the approved revision) with the human **Approve revision N** control (exact revision and content hash, approval scope, allowed open questions; one command id per dialog so a retry replays) and **Withdraw**; `StrategyDraftEditor` edits the template (claim-kind labels, `Unknown` baselines/targets, impact proposal) and keeps its unsaved text through a CAS refusal, showing the stored draft beside it (a later `strategy-detail` push replaces it), and **Reload stored draft** adopts exactly that shown draft, so the next save is CAS-based on it; **Submit draft for review** sends the human draft. `StrategyRevisionHistory` lists every revision (expandable content — superseded and withdrawn stay accessible), the drafts, recorded decisions, and the pending impact-review item. Human actions go over the chat WebSocket (`strategy-save-draft`/`submit`/`approve`/`withdraw`, answered by `strategy-result`; authoritative `strategy-snapshot`/`strategy-detail` pushes on every committed change). Every control disables while disconnected; refusals and stale errors show inline.
- Profile routing (group settings): `profiles: [a, b]` or `{ a: 2, b: 1 }` (single-line flow values; order = preference; the map caps live group members per profile — every non-archived member counts, user-created or spawned, busy or parked, plus pending spawns — and `max` defaults to the caps' sum; a single `profile` still works; unknown ids are warned and dropped), `strategy: first-available|profile-order` (built-in routing; both skip cooling profiles; members always beat spawning), and `onLimit: { parkIfResetWithin: 3h, otherwise: forward|release, forwardTo: <group or session> }` (invalid values are warnings, defaults apply). The groups route returns these warnings and per-profile caps with live counts; the New Session dialog warns (never refuses) when a profile's cap is reached. See `docs/routing/README.md`.
- Routing rules: `~/.kawai/routing/<group>.ts` only (never project files) default-exports `{ route, onLimit?, env?, timeoutMs? }`, typed by `kawai-routing.d.ts` that kawai publishes beside them from `src/shared/routing.ts` (type-only, so it is copied verbatim). Each rule runs in a Bun Worker: a bootstrap Worker with `env: {}` reads its declared `env`, then the serving Worker gets exactly those variables; calls time out (default 3 s, max 10 s; restarted after 3 consecutive timeouts). Rules load at server start and on **Reload routing rules** (`team-mailbox-reload-rules` → `team-mailbox-rules-result`; every mailbox snapshot carries `routing: { rules, decisions }`); file edits alone never apply. `src/server/team/routing/`: `ruleLoader.ts`/`ruleHost.ts`/`ruleWorker.ts` (runtime), `candidates.ts` + `builtin.ts` (pure), `router.ts` (decisions, holds, per-group log).
- Group mail is routed one message at a time (`dispatcher.ts`): per pass urgent direct, urgent group, normal direct, normal group; groups route concurrently, one decision at a time within a group. The router sees idle, available, request-free, non-parked members in the task's worktree plus spawn slots staffing allows (`staffing.spawnContext`/`spawnFor`, whose reservation transaction re-counts per-profile caps; `team_spawns.profile_id`). Rules see metadata (priority, sender group, tags, worktree, task id; never the body), candidates (cooling ones included), caps/live counts, and per-profile usage (with `source`: push/report/pull) and limit events. Throws, timeouts, and unknown picks fall back to the built-in strategy; a stale pick is re-routed once, then built-in; holds wait for their retry time or a candidate change. Urgent direct mail never consults a rule.
- Limits: the driver reports rate-limit/billing/overload errors and any 429 (`limitSignals.ts`: `api_retry` = non-final, failed assistant message = final, reset from a rejected `rate_limit_event`) into `profile_limit_events` (24 h). Cooldown is computed: latest final event's reset, else +1 h; per profile across all groups. When the turn handling a delivered message ends after a final limit (`limitOutcomes.ts`), the message is parked (state `parked`, resume mail scheduled at the reset, holder paused — `Session.parked` badge/header — and skipped by group routing; a successful turn unparks; released after 3 parks), released (back to the group queue; direct mail to the holder's group), or forwarded (new message with a `handoff` package: progress digest, last error, claim commit from `git rev-parse HEAD` at claim, inspect-first instruction; `excluded_profile` keeps it off the limited profile; `team_handoff_notes` tells the original agent who took it once its profile recovers). The rule's `onLimit`, else group `onLimit`, decides. The human can **Hand off** parked work (`team-mailbox-hand-off`). Urgent direct mail (send or reply) to an agent whose profile is cooling is refused with the cooldown end.
- Mail delivery is acknowledged only by the recipient's complete CLI transcript row carrying its id, never by a push or display event. Startup reconciliation requeues unpushed claims, confirms recorded receipts, and requeues a pushed message absent from a clean transcript. Missing, unreadable, or torn transcripts hold the message as uncertain for human resolution; retry targets the same recipient with a possible-duplicate notice, or the human explicitly discards it.
- Every message state change is recorded in the append-only `team_message_events` table (`messageEvents.ts`, written inside `MailboxStore`'s transitions so none can escape logging): `sent` (or `dead-lettered` when the hop limit is already over), `reserved`, `claimed`, `held-for-request`, `pushed`, `delivered`, `requeued`, `held-uncertain`, `retried`, `cancelled`, `discarded`, `dead-lettered`, `parked`, `unparked`, `released`, `forwarded`. Each row carries a per-message sequence, the actor (`human` for the composer's send and the UI's cancel/retry/discard, `system` for delivery, recovery, and limit outcomes), the facts the update overwrote (previous state, claimant, recipient, reason), and the reason the transition wrote. Events are durable rows that survive restart with their messages; history reads one message's events or every event of a thread.
- Chat header (`ChatHeader.tsx`): line one is a status dot and word plus the click-to-rename name; line two is profile · model · project with task and paused chips. Then the context meter, the side-panel switcher (Tasks, Mailbox, Messages, Strategy; one open at a time through `sideSlot.ts`'s `toggleSideSlot`), the **Auto-approve** switch, and the ⋯ session menu (Rename, Debug, Archive, Kill session — kill asks first). `useHeaderLayout` steps by the header's own width in chat-font ems: labelled entries, then icons, then panels folded into the menu with a percentage-only meter.
- Chat sessions can be archived (`archived_at` in `chat_sessions`; **Archive** in the chat header's session menu or the navigator row): archiving stops the agent but keeps the record, conversation, and protocol log; archived chats open read-only (no agent starts; Restore resumes the same conversation) and are exempt from the history lookback. Kill is still the only permanent removal.
- Unsubmitted composer input is a per-session client-side draft (keyed by session id in `chatStore.drafts`): it survives switching chats and reconnects and returns after archive → restore, clears on submit, and is discarded on kill; it is never sent to the server or restored after a page reload.
- Navigator: live sessions sit in OpenSpec change/worktree sections; hibernating, history, and archived sessions collect in the docked `Archive` pane (newest first, collapsed until first expanded). `Remote` holds only live sessions on other hosts.

## Structure

- src/server/     Hono backend, WebSocket, tmux/pty management, log parsing
  - `src/server/SessionManager.ts` - tmux window discovery, log parsing, status detection
  - `src/server/index.ts` - Hono routes, WebSocket handling
  - `src/server/chat/` - SDK driver, session lifecycle, transcript replay, subscriptions, and development fixture
  - `src/server/chat/wireTap.ts`, `ChatWireLog.ts`, `ChatWireLogs.ts` - always-on raw protocol capture for the chat debug view
  - `src/server/strategy/` - product strategy store, service, agent tools, and human-action connections
- src/client/     React frontend, xterm.js terminal, Zustand stores
  - `src/client/App.tsx` - main UI, keyboard shortcuts
  - `src/client/components/Terminal.tsx` - xterm.js wrapper
  - `src/client/components/chat/` - transcript, approvals, questions, and composer
  - `src/client/components/chat/ProductStrategyPanel.tsx`, `StrategyDraftEditor.tsx`, `StrategyRevisionHistory.tsx` - strategy view, draft editor, and revision history
  - `src/client/stores/chatStore.ts` - ordered transcript and pending requests
  - `src/client/components/chat/ChatDebugPanel.tsx`, `src/client/stores/chatDebugStore.ts` - protocol-frame panel behind the session menu's Debug toggle
- src/shared/     Shared types
  - `src/shared/chat.ts` - SDK-independent chat events and request contracts
  - `src/shared/productStrategy.ts` - SDK-independent strategy records, template content, claim kinds, and canonical hashing

- Data directory: `~/.agentboard/` contains `agentboard.db` (session data), `agentboard.log`, and `chat-wire/` (per-chat-session raw protocol logs, beside the DB)

## Git

- Check `git status`/`git diff` before commits
- Atomic commits; push only when asked
- Never destructive ops (`reset --hard`, `force push`) without explicit consent
- Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`
- Commit early and often — make small, incremental commits as you work rather than one large commit at the end.
